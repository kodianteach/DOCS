# Historia #2: Flujo Completo de Creación, Activación y Onboarding de Administradores

**Estado:** Lista para Revisión (Developer)

---

## Historia de Usuario

**Como** administrador pre-registrado de una ciudadela, conjunto residencial o condominio en la plataforma ATLAS con rol ADMIN_ATLAS,  
**Quiero** recibir un correo con credenciales temporales, activar mi cuenta mediante un token seguro estableciendo mi contraseña definitiva, instalar la PWA en mi dispositivo móvil, y completar el onboarding creando mi organización con sus datos básicos,  
**Para** tener acceso completo y seguro a mi tenant en la plataforma ATLAS y poder gestionar mi propiedad horizontal de forma autónoma desde cualquier dispositivo.

## Descripción

Se requiere implementar el flujo completo de creación, activación y onboarding de administradores en la PWA atlas-platform, integrándose con los endpoints existentes del backend (`/api/external/admin/*`). El flujo cubre: (1) una pantalla oculta de backoffice para que el equipo de desarrollo pre-registre administradores, (2) la validación de token y formulario de activación donde el admin cambia su contraseña temporal, (3) un prompt de instalación PWA post-activación para acceso móvil, y (4) un componente de onboarding obligatorio donde el admin ACTIVATED crea su Company y Organization. El backend ya cuenta con los use cases (`PreRegisterAdminUseCase`, `ActivateAdminUseCase`, `CompleteOnboardingUseCase`) y endpoints funcionales. Esta historia se enfoca en la implementación frontend con validaciones complementarias en el backend para control de errores y mensajes al usuario.

## Criterios de Aceptación

### Escenario 1: Acceso a pantalla de activación con token válido

- **Dado** que un administrador pre-registrado recibió un correo con un enlace de activación conteniendo un token válido
- **Cuando** accede a la URL de activación en la PWA (ruta `/activate?token=...`)
- **Entonces** el sistema valida el token contra `GET /api/external/admin/validate-token?token={token}`, confirma que es válido y no expirado, y muestra el formulario de activación con los campos: correo electrónico, contraseña temporal, nueva contraseña y confirmación de nueva contraseña

### Escenario 2: Token inválido o expirado

- **Dado** que un usuario accede a la ruta `/activate` con un token inválido, expirado o malformado
- **Cuando** el sistema valida el token contra el backend
- **Entonces** se muestra un mensaje de error claro en pantalla: "El enlace de activación es inválido o ha expirado. Contacta al equipo de soporte para solicitar un nuevo enlace" y NO se muestra el formulario de activación

### Escenario 3: Token ya consumido (single-use)

- **Dado** que un usuario accede a la ruta `/activate` con un token que ya fue utilizado previamente
- **Cuando** el sistema valida el token contra el backend y recibe estado `CONSUMED`
- **Entonces** se muestra un mensaje de error en pantalla: "Este enlace de activación ya fue utilizado. Si ya activaste tu cuenta, inicia sesión normalmente" con un enlace/botón para ir a `/login`

### Escenario 4: Activación exitosa con cambio de contraseña

- **Dado** que el formulario de activación está visible con un token válido
- **Cuando** el administrador ingresa su correo electrónico, la contraseña temporal recibida por correo, una nueva contraseña que cumple las políticas de seguridad, y la confirmación coincidente, y presiona "Activar Cuenta"
- **Entonces** el sistema envía `POST /api/external/admin/activate` con los datos, el backend valida las credenciales temporales, actualiza la contraseña, cambia el estado del usuario a `ACTIVATED`, marca el token como consumido, registra en auditoría, y el frontend muestra un mensaje de éxito: "¡Tu cuenta ha sido activada exitosamente!"

### Escenario 5: Contraseña no cumple políticas de seguridad

- **Dado** que el formulario de activación está visible
- **Cuando** el administrador ingresa una nueva contraseña que no cumple la política (mínimo 8 caracteres, al menos 1 mayúscula, 1 minúscula y 1 número)
- **Entonces** el sistema muestra un mensaje de validación en tiempo real debajo del campo: "Debe contener mayúscula, minúscula y número (mínimo 8 caracteres)" y el botón "Activar Cuenta" permanece deshabilitado

### Escenario 6: Contraseñas no coinciden

- **Dado** que el formulario de activación está visible
- **Cuando** el administrador ingresa una nueva contraseña y una confirmación que no coincide
- **Entonces** el sistema muestra un mensaje de validación debajo del campo de confirmación: "Las contraseñas no coinciden" y el botón "Activar Cuenta" permanece deshabilitado

### Escenario 7: Error de credenciales temporales incorrectas

- **Dado** que el formulario de activación está visible con token válido
- **Cuando** el administrador ingresa un correo o contraseña temporal que no coinciden con los registrados en el backend
- **Entonces** el sistema muestra un mensaje de error del backend en pantalla: "Las credenciales temporales son incorrectas. Verifica el correo y la contraseña enviados a tu email" sin revelar cuál de los dos campos es incorrecto

### Escenario 8: Prompt de instalación PWA post-activación

- **Dado** que la activación fue exitosa y el usuario está en un dispositivo compatible con instalación de PWA
- **Cuando** se muestra la pantalla de éxito de activación
- **Entonces** se presenta un modal informativo indicando: "Descarga ATLAS en tu dispositivo para acceder fácilmente" con un botón "Instalar aplicación" que activa el prompt nativo del navegador (usando `PwaUpdateService.promptInstall()`), y un enlace secundario "Continuar en el navegador" para omitir la instalación

### Escenario 9: Redirección a onboarding después del primer login (solo ADMIN_ATLAS con estado ACTIVATED)

- **Dado** que un usuario con rol `ADMIN_ATLAS` y estado `ACTIVATED` (sin Company/Organization creada) inicia sesión exitosamente
- **Cuando** el sistema evalúa el estado del usuario post-login
- **Entonces** redirige automáticamente a la ruta `/onboarding` en lugar de `/home`, bloqueando el acceso a cualquier otra funcionalidad hasta completar el onboarding. Usuarios con otros roles (`OWNER`, `ADMIN_CONJUNTO`, etc.) o con estado `ACTIVE` NO son redirigidos al onboarding

### Escenario 10: Onboarding exitoso — creación de Company y Organization

- **Dado** que un administrador `ACTIVATED` con rol `ADMIN_ATLAS` está en la pantalla de onboarding (`/onboarding`)
- **Cuando** completa todos los campos obligatorios: nombre de la organización (equivalente al nombre de la compañía), dirección, NIT, teléfono, tipo de propiedad (CIUDADELA, CONJUNTO o CONDOMINIO), y presiona "Completar Registro"
- **Entonces** el sistema envía `POST /api/external/admin/complete-onboarding` con los datos mapeados, el backend crea la Company y Organization, asocia al usuario como administrador principal, cambia el estado a `ACTIVE`, activa el tenant, y el frontend muestra mensaje de éxito y redirige a `/home` con acceso completo

### Escenario 11: Onboarding — validaciones de campos requeridos

- **Dado** que el administrador está en la pantalla de onboarding
- **Cuando** intenta enviar el formulario sin completar los campos obligatorios (nombre de organización, dirección, NIT, teléfono, tipo de propiedad)
- **Entonces** el sistema muestra mensajes de validación en cada campo faltante: "Este campo es obligatorio" y el botón "Completar Registro" permanece deshabilitado hasta completar todos los campos requeridos

### Escenario 12: Pre-registro de administrador desde backoffice oculto

- **Dado** que un desarrollador del equipo accede a la pantalla oculta de backoffice (ruta no listada en navegación, accesible por URL directa)
- **Cuando** completa el formulario con los datos del nuevo administrador: nombre completo, correo electrónico, tipo de documento, número de documento y teléfono, y presiona "Pre-registrar Administrador"
- **Entonces** el sistema envía `POST /api/external/admin/pre-register` con header `X-Operator-Id`, el backend crea el usuario con estado `PRE_REGISTERED`, asigna rol `ADMIN_ATLAS`, genera token y contraseña temporal, envía correo de activación, y el frontend muestra confirmación: "Administrador pre-registrado exitosamente. Se ha enviado el correo de activación a {email}"

### Escenario 13: Errores del backend mostrados en pantalla

- **Dado** que el usuario está interactuando con cualquier formulario del flujo (activación, onboarding o pre-registro)
- **Cuando** el backend retorna un error (email duplicado, NIT ya registrado, error de validación, error de servidor, timeout de conexión)
- **Entonces** el frontend captura el error, extrae el mensaje del backend y lo muestra como alerta visible en la pantalla del formulario correspondiente, sin exponer detalles técnicos internos al usuario

## Información Recopilada

### Usuario y Contexto

- **Tipo de usuario:** Administrador de propiedad horizontal (ciudadela, conjunto residencial o condominio) con rol `ADMIN_ATLAS`
- **Permisos requeridos:** El pre-registro lo realiza el equipo de desarrollo vía backoffice oculto. La activación y onboarding los realiza el administrador pre-registrado. Post-onboarding, el `ADMIN_ATLAS` tiene permisos completos dentro de su organización (multi-tenant estricto)
- **Valor de negocio:** Habilitar el flujo completo para que nuevos administradores de propiedades horizontales puedan auto-activarse de forma segura, configurar su organización y comenzar a operar la plataforma de forma autónoma, reduciendo la intervención manual del equipo de desarrollo

### Reglas de Negocio

1. **Solo ADMIN_ATLAS hacen onboarding:** Únicamente usuarios con rol `ADMIN_ATLAS` y estado `ACTIVATED` son redirigidos al flujo de onboarding. Otros roles no pasan por este flujo
2. **Token single-use con expiración:** El token de activación tiene expiración de 24 horas y solo puede usarse una vez. Al consumirse se marca como `CONSUMED` y no puede reutilizarse
3. **Política de contraseña:** Mínimo 8 caracteres, al menos 1 letra mayúscula, 1 letra minúscula y 1 número. Caracteres especiales permitidos: `@$!%*?&`. Ya implementada en frontend como `CustomValidators.strongPassword()`. Debe validarse también en el backend
4. **Contraseñas deben coincidir:** La nueva contraseña y su confirmación deben ser idénticas. Ya implementada en frontend como `CustomValidators.mustMatch()`
5. **Onboarding obligatorio y único:** El administrador ACTIVATED no puede acceder a ninguna funcionalidad hasta completar el onboarding. Se realiza una única vez por administrador
6. **Backoffice solo para desarrolladores:** La pantalla de pre-registro es una ruta oculta no visible en la navegación, accesible solo por URL directa para uso exclusivo del equipo de desarrollo
7. **Multi-tenant estricto:** Todo dato queda aislado por `organizationId`. Prohibido acceso cruzado entre organizaciones
8. **Auditoría obligatoria:** El backend registra cada acción del flujo (pre-registro, envío de email, activación, onboarding) con datos de quién, cuándo, IP y user-agent
9. **Tipos de organización:** CIUDADELA (zonas → torres → apartamentos/casas), CONJUNTO (zonas opcionales → apartamentos/casas), CONDOMINIO (zonas → casas únicamente). La configuración de zonas y unidades se define en el onboarding según el tipo seleccionado
10. **Unidades en flujo separado:** La creación de torres, zonas y unidades habitacionales NO se realiza en el onboarding — eso corresponde a otro flujo posterior

### Interfaz

- **Pantalla de activación (`/activate?token=...`):** Formulario centrado con diseño consistente con el login existente (tarjeta centrada con gradiente naranja `--gradient-primary`, logo ATLAS). Campos: correo, contraseña temporal, nueva contraseña, confirmación. Reutilizar `FormFieldComponent`, `TextInputComponent`, `ButtonComponent` del design system existente (Atomic Design)
- **Modal de instalación PWA:** Se muestra post-activación exitosa. Utiliza `PwaUpdateService` ya implementado. Incluye botón "Instalar" y enlace "Continuar en navegador"
- **Pantalla de onboarding (`/onboarding`):** Componente nuevo. Formulario con campos: nombre organización, dirección, correo (opcional), NIT, teléfono, tipo de propiedad (select con CIUDADELA/CONJUNTO/CONDOMINIO). Diseño coherente con el design system existente
- **Pantalla de backoffice (`/dev/admin-register` o ruta oculta similar):** Formulario para pre-registro con campos: nombre completo, correo, tipo documento (CC, CE, NIT, PA, TI, PEP), número documento, teléfono
- **Navegación:** No se agregan items en la navegación para activación ni backoffice. La ruta `/onboarding` aplica redirección automática post-login para `ADMIN_ATLAS` con estado `ACTIVATED`

### Sistemas Externos

- No se integran sistemas externos adicionales. Todas las operaciones se realizan contra el backend Atlas existente mediante los endpoints `/api/external/admin/*`

## Análisis Arquitectónico (Arquitecto)

### Decisiones de Diseño

**Patrón Arquitectónico:** Clean Architecture Frontend (Domain → Gateway → Use Case → Adapter) + Atomic Design (Atoms → Molecules → Organisms → Templates → Pages)

**Justificación:** Es el patrón ya establecido en el proyecto y validado en HU #1 (Login Multitenant). El `AuthAdapter` con `Result<T>`, los gateways abstractos, y la estructura de componentes Atomic Design ya funcionan y están probados. Seguir el mismo patrón garantiza coherencia arquitectónica, facilita onboarding de desarrolladores y permite reutilizar componentes existentes (`FormFieldComponent`, `ButtonComponent`, `SelectInputComponent`, `CustomValidators`). No se justifica introducir patrones alternativos dado que la arquitectura existente cubre perfectamente los requerimientos de esta historia.

### Validación de Impacto

**Código verificado:** Se leyeron y analizaron 25+ archivos del frontend y backend. Hallazgos principales:

- **Endpoints backend funcionales:** Los 4 endpoints en `/api/external/admin/*` (pre-register, validate-token, activate, complete-onboarding) están completamente implementados con DTOs, handlers, routers y use cases. No requieren cambios funcionales salvo la validación de contraseña.
- **Frontend sin páginas de activación/onboarding:** No existe página `/activate`, `/onboarding` ni `/dev/admin-register`. Deben crearse desde cero siguiendo los patrones existentes.
- **Componentes reutilizables confirmados:** `FormFieldComponent`, `ButtonComponent`, `SelectInputComponent`, `CustomValidators.strongPassword()`, `CustomValidators.mustMatch()`, `PwaUpdateService.promptInstall()` — todos verificados y disponibles.
- **JWT actual limitado:** El modelo `AuthUser` solo tiene `id`, `email`, `name`, `role` (singular). El JWT real del backend incluye `status`, `roles[]`, `permissions[]`, `organizationId`, `enabledModules[]`. Debe extenderse el modelo.
- **Inconsistencias detectadas:** `AuthenticationService` y `AdminProfileService` usan `localStorage` directo en lugar de `StorageGateway`. Los nuevos adapters deben usar exclusivamente `StorageGateway`. Existen dos versiones de `profileCompletionGuard` (una en `guards/` y otra en `infrastructure/guards/`). Se registra como deuda técnica.
- **Riesgo de pre-registro sin protección:** La ruta `/dev/admin-register` será pública/oculta. Aceptable para MVP pero debe documentarse como deuda técnica.

### Notas Técnicas

- **Contratos Frontend ↔ Backend:** `ActivationGateway.validateToken(token)` → `GET /api/external/admin/validate-token?token={token}` devuelve `TokenValidationResult`. `ActivationGateway.activate(request)` → `POST /api/external/admin/activate` con body `{token, email, currentPassword, newPassword}`. `OnboardingGateway.completeOnboarding(request)` → `POST /api/external/admin/complete-onboarding`. `PreRegistrationGateway.preRegister(request)` → `POST /api/external/admin/pre-register` con header `X-Operator-Id`.
- **Guards encadenados:** `authGuard` verifica token JWT en StorageGateway → redirige a `/login` si ausente. `onboardingGuard` post-autenticación verifica si `role === ADMIN_ATLAS` y `status === ACTIVATED` → redirige a `/onboarding` si no completó onboarding.
- **Deuda técnica identificada:** (1) Refactorizar `AuthenticationService` y `AdminProfileService` para usar `StorageGateway` en lugar de `localStorage` directo. (2) Consolidar guards duplicados. (3) Proteger `/dev/admin-register` con autenticación en versión futura.

Implica integración con 4 endpoints existentes, validaciones frontend+backend sincronizadas, y flujo multi-paso (activación → PWA → login → onboarding). Los componentes UI reutilizables ya existen (`FormFieldComponent`, `ButtonComponent`, `SelectInputComponent`, `CustomValidators`, `PwaUpdateService`), lo que reduce complejidad de UI pero no la de orquestación.

**Riesgos técnicos conocidos:**
1. **Coexistencia legacy:** `LoginPageComponent` usa `AuthenticationService` (legacy, `localStorage` directo) en vez de `AuthGateway` (Clean Architecture). La modificación del login (Fase 9) debe usar `AuthGateway` para la evaluación de status, pero no puede eliminar `AuthenticationService` aún porque otras partes del sistema dependen de él. Riesgo de duplicación temporal de lógica.
2. **Modelo AuthUser incompleto:** El modelo actual solo tiene `{id, email, name, role}`. El JWT del backend incluye `status`, `roles[]`, `permissions[]`, `organizationId`, `enabledModules[]`, `defaultRoute`. Si el backend no envía `status` en el JWT actual, la redirección a `/onboarding` post-login no funcionará → validar que el endpoint de login devuelve `status` en la respuesta.
3. **Sin tests backend existentes para HU #2:** No existen tests unitarios para `PreRegisterAdminUseCase`, `ActivateAdminUseCase`, ni `CompleteOnboardingUseCase`. No hay test data builders. Se deben crear tests para la nueva validación de contraseña (Fase 12).
4. **Ruta `/dev/admin-register` sin protección:** Será pública y accesible por URL directa. Aceptable para MVP pero documentada como deuda técnica.
5. **Guards duplicados:** Existen dos `profileCompletionGuard` (uno legacy en `guards/`, otro clean arch en `infrastructure/guards/`). Los nuevos guards se crean exclusivamente en `infrastructure/guards/`.

**Patrones y convenciones del equipo:**
- **Clean Architecture Frontend:** domain/models → domain/gateways (abstractos) → domain/use-cases → infrastructure/adapters (implementan gateways) → presentation/pages + presentation/ui (Atomic Design)
- **Result<T>:** Patrón establecido en `AuthAdapter` — `Result.success(data)` / `Result.failure(error)` para comunicación gateway→adapter
- **Gateways abstractos:** Clases abstractas TypeScript con métodos que retornan `Observable<Result<T>>`
- **Adapters HTTP:** Inyectan `HttpClient`, manejan errores con `catchError` diferenciado (400→mensaje usuario, 401→sesión expirada, 500→error genérico)
- **Guards como CanActivateFn:** Funciones exportadas (no clases), inyectan servicios con `inject()`, retornan `boolean | UrlTree`
- **Componentes standalone:** Todos los componentes usan `standalone: true`, `changeDetection: ChangeDetectionStrategy.OnPush`, signals para estado reactivo
- **Path aliases:** `@domain/`, `@infrastructure/`, `@presentation/`, `@env/` configurados en `tsconfig.json`
- **Backend reactivo:** Reactor `Mono<T>`, validaciones en use cases (no en DTOs), inner records para commands/results
- **Naming backend:** `XxxUseCase.java` para casos de uso, `XxxHandler.java` para entry points, `XxxRequest/Response` para DTOs

**Dependencias nuevas a instalar:**
Ninguna — todas las dependencias necesarias ya están en el proyecto (Angular 17+, RxJS, HttpClient, ReactiveFormsModule, PwaUpdateService, JavaMailSender, Spring Security Crypto)

**Estrategia de testing:**
Frontend: Jasmine + Karma (`describe/it/expect`, `jasmine.createSpyObj()` para mocks, `ComponentFixture` para componentes) | Backend: JUnit 5 + Reactor Test (`StepVerifier`), WebTestClient para integración, AssertJ para aserciones | Tests requeridos: FE → spec para cada page, organism, guard, adapter y use-case; BE → test unitario para validación de contraseña en `ActivateAdminUseCase` | Cobertura: ≥70% líneas (JaCoCo BE), best-effort FE | Builders: No existen test data builders — crear `AuthUserBuilder` y `TokenBuilder` para backend si se requieren datos complejos
