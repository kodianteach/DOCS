# Historia #7: Validación en Portería — Scanner QR Online/Offline

**Estado:** En Desarrollo (Developer)

---

## Historia de Usuario

**Como** portero con acceso a un dispositivo de portería enrolado en la plataforma ATLAS,  
**Quiero** escanear el QR de una autorización de ingreso y validar su autenticidad, vigencia y datos (incluyendo vehículo si aplica) tanto con conexión a internet como sin ella, y registrar los eventos de entrada y salida de vehículos,  
**Para** controlar de forma segura el acceso de personas y vehículos a la propiedad horizontal sin depender de la conectividad a internet para la validación básica.

## Descripción

Se requiere implementar la funcionalidad de validación de autorizaciones en la PWA del dispositivo de portería. El portero escanea el QR presentado por el visitante y el sistema valida la autorización en dos niveles: (1) **Validación offline obligatoria** — verifica la firma digital del QR usando la clave pública almacenada localmente, valida que la fecha/hora actual esté dentro del rango autorizado (con tolerancia de ±10 minutos por clock skew), y si hay datos de vehículo, el portero confirma visualmente la coincidencia. (2) **Validación online adicional** (cuando hay conexión) — consulta al servidor si la autorización está revocada o tiene restricciones adicionales, y registra el evento de acceso en tiempo real. Si no hay conexión, los eventos se almacenan localmente en IndexedDB y se sincronizan automáticamente cuando se restablece la conectividad. La aplicación mantiene un proceso de sincronización continua en segundo plano para actualizar la lista de revocaciones.

## Criterios de Aceptación

### Escenario 1: Validación offline exitosa — Firma válida y fecha vigente

- **Dado** que el dispositivo de portería está enrolado y tiene la clave de verificación almacenada localmente, y **no hay conexión a internet**
- **Cuando** el portero escanea un QR de una autorización cuya firma es válida y la fecha/hora actual está dentro del rango `validFrom` — `validTo` (con tolerancia de ±10 minutos)
- **Entonces** el sistema muestra: ✅ "Autorización VÁLIDA" con los datos del autorizado (nombre, documento, tipo de servicio, unidad) y el portero puede habilitar el paso. El evento se almacena en cola local para sincronización posterior

### Escenario 2: Validación offline fallida — Firma inválida

- **Dado** que el dispositivo de portería está sin conexión
- **Cuando** el portero escanea un QR cuya firma digital no coincide con la clave pública almacenada (QR manipulado o de otra organización)
- **Entonces** el sistema muestra: ❌ "Autorización INVÁLIDA — QR no reconocido" y se rechaza el acceso. El evento se registra localmente como `ACCESS_DENIED`

### Escenario 3: Validación offline fallida — Autorización fuera de rango de fechas

- **Dado** que el dispositivo de portería está sin conexión
- **Cuando** el portero escanea un QR cuya firma es válida pero la fecha/hora actual está fuera del rango `validFrom` — `validTo` (considerando tolerancia de ±10 minutos)
- **Entonces** el sistema muestra: ❌ "Autorización EXPIRADA o NO VIGENTE — Válida desde [fecha] hasta [fecha]" y se rechaza el acceso

### Escenario 4: Validación con vehículo — Confirmación visual del portero

- **Dado** que la autorización incluye datos de vehículo (placa, tipo, color)
- **Cuando** el portero escanea el QR
- **Entonces** el sistema muestra los datos del vehículo esperado (placa: ABC123, tipo: Carro, color: Rojo) y solicita al portero confirmar visualmente: "¿El vehículo coincide con los datos autorizados?" con opciones Sí/No. Si coincide, se registra `vehicleMatch: true`. Si no coincide, se alerta al portero pero puede decidir permitir o denegar (la decisión se registra)

### Escenario 5: Validación online — Autorización revocada

- **Dado** que el dispositivo de portería **tiene conexión a internet**
- **Cuando** el portero escanea un QR cuya firma y fechas son válidas, pero al consultar el servidor la autorización fue revocada
- **Entonces** el sistema muestra: ❌ "Autorización REVOCADA — Esta autorización fue cancelada por el administrador/creador" y se rechaza el acceso. El evento se registra en el servidor en tiempo real

### Escenario 6: Validación online — Registro de acceso en tiempo real

- **Dado** que el dispositivo de portería tiene conexión a internet y la autorización es válida (firma, fechas, no revocada)
- **Cuando** el portero confirma el ingreso del visitante
- **Entonces** el sistema registra el evento de acceso en el backend: `porteroUserId`, `unitId`, datos del vehículo (si aplica), acción (`ENTRY`), `createdBy: portero`, y muestra confirmación del registro. Se registran eventos de auditoría `ACCESS_GRANTED` y `ACCESS_LOG_CREATED`

### Escenario 7: Sincronización de eventos offline al recuperar conexión

- **Dado** que el dispositivo estuvo sin conexión y acumuló eventos de acceso en la cola local (IndexedDB)
- **Cuando** se restablece la conexión a internet
- **Entonces** la PWA sincroniza automáticamente todos los eventos pendientes al backend, registrando para cada uno: `authId`, `timestamp`, resultado (permitido/denegado), `porteroUserId`, `deviceId`, `vehicleMatch`, y marca los eventos locales como sincronizados

### Escenario 8: Sincronización continua de lista de revocaciones

- **Dado** que el dispositivo de portería está enrolado y tiene conexión a internet
- **Cuando** la aplicación está activa
- **Entonces** la PWA mantiene un proceso de sincronización periódica en segundo plano que actualiza: la lista de autorizaciones revocadas, claves criptográficas actualizadas (si aplica), y configuraciones de la organización. Esta actualización se ejecuta con frecuencia regular para minimizar el riesgo de aceptar un QR revocado en modo offline

### Escenario 9: Flujo de salida de vehículo

- **Dado** que un vehículo necesita salir de la propiedad horizontal
- **Cuando** el portero selecciona la opción "Registrar Salida de Vehículo"
- **Entonces** el sistema solicita: placa del vehículo y datos de la persona que retira el vehículo (nombre). El portero puede buscar por placa en los registros de acceso recientes. Al confirmar, se registra el evento con acción `EXIT` incluyendo `porteroUserId`, placa del vehículo y datos de la persona. Si no hay conexión, se almacena localmente para sincronización posterior

### Escenario 10: Salida de persona sin vehículo

- **Dado** que un visitante sin vehículo desea salir de la propiedad
- **Cuando** el visitante se dirige a la portería
- **Entonces** **no es necesario** presentar QR ni registrar la salida. La salida de personas sin vehículo no requiere proceso en el sistema

### Escenario 11: Scanner QR — Interfaz del portero

- **Dado** que el portero activa la función de escaneo QR desde la pantalla principal de portería
- **Cuando** se abre el scanner
- **Entonces** se activa la cámara del dispositivo con un marco de escaneo visible, el QR se detecta automáticamente, y el resultado de la validación se muestra inmediatamente con indicadores visuales claros (verde para válido, rojo para inválido)

### Escenario 12: Error al escanear QR ilegible o no válido

- **Dado** que el portero escanea algo que no es un QR de autorización válido
- **Cuando** el código escaneado no tiene el formato esperado (payload + firma)
- **Entonces** el sistema muestra: "El código escaneado no es una autorización válida de ATLAS" y permite reintentar el escaneo

## Información Recopilada

### Usuario y Contexto

- **Tipo de usuario:** Portero (usuario con rol de portería) operando desde un dispositivo de portería enrolado
- **Permisos requeridos:** `AUTHORIZATIONS_VALIDATE`, `ACCESS_LOG_CREATE`, `VEHICLES_VALIDATE` (asignados al portero en HU #4)
- **Valor de negocio:** Garantizar el control de acceso seguro a la propiedad horizontal con capacidad de funcionar offline, validando criptográficamente que las autorizaciones son auténticas y vigentes, y registrando todos los eventos de acceso para trazabilidad

### Reglas de Negocio

1. **Offline-first:** La validación de firma digital + rango de fechas DEBE funcionar sin conexión. Es el mínimo obligatorio. La validación online agrega capas adicionales (revocación, registro en tiempo real)
2. **Tolerancia de reloj:** ±10 minutos (`maxClockSkewMinutes`) para compensar diferencias de reloj entre dispositivos
3. **Múltiples entradas por rango:** El mismo QR puede presentarse múltiples veces mientras esté dentro del rango de fechas. No es entrada única
4. **Revocación solo verificable online:** Si el portero está offline, NO puede saber si una autorización fue revocada. Mitigación: sincronización continua de lista de revocaciones cuando hay conexión
5. **Cola local de eventos:** Todos los eventos de acceso generados offline se almacenan en IndexedDB y se sincronizan al recuperar conexión
6. **Salida de vehículos requiere registro:** Para retirar un vehículo, el portero debe registrar la placa y datos de la persona que retira. Para personas sin vehículo, la salida es libre y no requiere registro
7. **Verificación de firma criptográfica:** Extraer payload + firma del QR. Verificar firma con `verificationKey` local (clave pública EdDSA/JWK almacenada en WebCrypto). Si falla → RECHAZAR
8. **Auditoría obligatoria:** Registrar `ACCESS_GRANTED`, `ACCESS_DENIED`, `ACCESS_LOG_CREATED` con datos completos del evento

### Interfaz

- **Ubicación en navegación:** Opción "Portería" en el menú inferior **solo visible para usuarios con rol de portero**
- **Pantalla principal de portería:** Botón grande central "Escanear QR". Botón secundario "Registrar Salida de Vehículo". Indicador de estado de conexión (online/offline)
- **Scanner QR:** Cámara activa con marco de escaneo. Detección automática del QR
- **Resultado de validación:** Pantalla de resultado con fondo verde (✅ VÁLIDA) o rojo (❌ INVÁLIDA). Datos del autorizado visibles. Si incluye vehículo, confirmación visual del portero
- **Registro de salida de vehículo:** Formulario: Placa del vehículo (con búsqueda en accesos recientes), Nombre de la persona. Botón "Registrar Salida"
- **Indicador de sincronización:** Badge con número de eventos pendientes de sincronizar. Animación de sincronización en progreso
- **Diseño:** Priorizar usabilidad en pantallas grandes (tablets de portería). Botones grandes y visibles. Colores claros de resultado (verde/rojo)

### Sistemas Externos

- No se integran sistemas externos. Utiliza APIs del navegador: Camera API (scanner QR), IndexedDB (cola local), WebCrypto (verificación de firma), Service Worker (sincronización en segundo plano)

## Contexto y Referencias

**Arquitectura:** PWA offline-first. WebCrypto API para verificación de firma EdDSA. IndexedDB para cola de eventos offline. Service Worker para sincronización. Backend reactivo WebFlux.

**Historias relacionadas:** HU #4 (Creación de Portero) — define roles y permisos del portero. HU #5 (Enrolamiento Dispositivo) — instala la clave de verificación usada aquí. HU #6 (Generación de Autorizaciones) — genera los QRs que se validan aquí. HU #8 (Panel Administrativo de Accesos) — visualiza los eventos registrados por los porteros.

**Lecciones aprendidas:**
- La sincronización continua de revocaciones es la mitigación principal para el riesgo de aceptar un QR revocado offline
- La tolerancia de reloj de ±10 minutos previene rechazos falsos por diferencias de hora entre dispositivos
- El formato JWS (payload.signature) es autocontenido y verificable sin consultar al servidor

### Decisiones de Diseño

**Patrón Arquitectónico:** Offline-First PWA con Clean Architecture (Backend + Frontend) — 3 capas de validación: Offline (EdDSA + fechas), Revocaciones locales (IndexedDB cache), Online (backend verification + registro)

**Justificación:**

**1. Nueva tabla `access_events` (NO reusar `access_scan_log`):** La tabla existente `access_scan_log` está acoplada a `access_codes` vía FK NOT NULL (paradigma solicitud-aprobación con códigos UUID). HU #7 referencia `visitor_authorizations` (HU #6), necesita columnas `action` (ENTRY/EXIT), `vehicle_match`, `offline_validated`, `synced_at`, `device_id`. Diferencias irreconciliables sin breaking changes.

| Aspecto | access_scan_log (V2) | access_events (V16 — nuevo) |
|---------|----------------------|----------------------------|
| FK principal | access_code_id → access_codes | authorization_id → visitor_authorizations |
| Acciones | Solo ENTRY (implícita) | ENTRY / EXIT explícito |
| Vehículo | No registrado | vehicle_match BOOLEAN |
| Offline | No soportado | offline_validated, synced_at |
| Dispositivo | device_info (texto libre) | device_id (referencia) |

**2. Arquitectura Offline-First con 3 capas de validación:**
- **Capa 1 — Offline (obligatoria):** Verificación firma EdDSA con `crypto.subtle.verify("Ed25519")` + validación rango fechas con tolerancia ±10min. No requiere servidor.
- **Capa 2 — Revocaciones locales:** Cache de autorizaciones revocadas en IndexedDB, actualizado periódicamente cuando hay conexión. Si authId está en cache → rechazar.
- **Capa 3 — Online (adicional):** Consulta backend `/api/porter/validate-authorization` para verificar revocación en tiempo real y registrar evento.

**3. Cola de eventos pull-based (NO Background Sync API):** No existen Background Sync, @Scheduled, ni push notifications en el sistema. El patrón existente es pull-based (véase bulkSync de vehículos). Frontend almacena eventos en IndexedDB con estado PENDING, al detectar conexión flushea cola vía POST batch, backend responde con IDs confirmados.

**4. `html5-qrcode` para scanner (NO `ngx-scanner`):** Ligera (~35KB gzip), no requiere Angular wrapper, compatible con PWA offline, API sencilla start()/stop(), soporte flashlight. ngx-scanner depende de ZXing-JS (~200KB).

**5. DoormanBottomNav — "Salidas" reemplaza tab "Más":** El tab "Más" no tiene ruta asignada (dead button). Se reemplaza por "Salidas" con ruta /doorman/vehicle-exit.

**6. ValidationResultComponent unificado (reemplaza AccessGrantedModal):** Un solo componente que soporta ambos estados (valid/invalid) con fondo verde/rojo, en lugar de crear un segundo modal separado.

**7. Validación online server-side con EdDSA:** Cuando hay conexión, el backend también verifica la firma (no confiar solo en el frontend). Usa `java.security.Signature("Ed25519")` con clave pública de `organization_crypto_keys` (HU #5). Además verifica status ACTIVE en visitor_authorizations.

**Flujo de validación completo (frontend):**
```
Cámara → html5-qrcode detecta → QrParserService.parse(rawString) →
Ed25519VerificationService.verify(payload, signature, publicKey) →
if (!valid) → DENIED (firma inválida)
DateRangeValidator.check(validFrom, validTo, ±10min) →
if (!inRange) → DENIED (fuera de rango)
RevocationCacheService.isRevoked(authId) →
if (revoked) → DENIED (revocada)
if (online) → PorterApiGateway.validateOnline(signedQr) →
  if (server says revoked) → DENIED
→ GRANTED → VehicleConfirmation (si aplica) → Log event
```

### Notas Técnicas

1. **IndexedDB schema:**
   - Database: "atlas-porter-db"
   - Store 1: "pending-events" { keyPath: "id", autoIncrement: true }, Indexes: "syncStatus", "scannedAt"
   - Store 2: "revoked-authorizations" { keyPath: "authId" }, Indexes: "revokedAt"
   - Store 3: "crypto-keys" (desde HU #5 — CryptoStorageService)

2. **Ed25519 verify con WebCrypto:**
   ```
   const isValid = await crypto.subtle.verify(
     "Ed25519",
     publicKey,        // CryptoKey from IndexedDB
     signatureBytes,   // Uint8Array from base64url decode
     payloadBytes      // Uint8Array (raw payload string as bytes)
   );
   ```

3. **Tolerancia de reloj ±10 minutos:**
   ```
   const now = Date.now();
   const skew = 10 * 60 * 1000;
   const validFrom = new Date(payload.validFrom).getTime() - skew;
   const validTo = new Date(payload.validTo).getTime() + skew;
   return now >= validFrom && now <= validTo;
   ```

4. **Tabla SQL V16 — access_events:**
   ```sql
   CREATE TABLE access_events (
     id BIGINT AUTO_INCREMENT PRIMARY KEY,
     organization_id BIGINT NOT NULL,
     authorization_id BIGINT NULL,
     porter_user_id BIGINT NOT NULL,
     device_id VARCHAR(100),
     action VARCHAR(10) NOT NULL,
     scan_result VARCHAR(20) NOT NULL,
     person_name VARCHAR(200),
     person_document VARCHAR(50),
     vehicle_plate VARCHAR(20),
     vehicle_match BOOLEAN DEFAULT NULL,
     offline_validated BOOLEAN DEFAULT FALSE,
     notes TEXT,
     scanned_at TIMESTAMP NOT NULL,
     synced_at TIMESTAMP NULL,
     created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
     FOREIGN KEY (organization_id) REFERENCES organization(id),
     FOREIGN KEY (authorization_id) REFERENCES visitor_authorizations(id),
     FOREIGN KEY (porter_user_id) REFERENCES users(id),
     INDEX idx_ae_org (organization_id),
     INDEX idx_ae_auth (authorization_id),
     INDEX idx_ae_porter (porter_user_id),
     INDEX idx_ae_action (action),
     INDEX idx_ae_scanned_at (scanned_at)
   );
   ```
