# Historia #3: Creación Masiva de Unidades con Configuración de Organización

**Estado:** Lista para Revisión (Developer) - Pendiente: Tests unitarios

---

## Historia de Usuario

**Como** administrador con rol `ADMIN_ATLAS` y permisos de gestión de unidades (`UNITS_DISTRIBUTE`) en la plataforma ATLAS,  
**Quiero** generar unidades habitacionales de forma masiva especificando un rango numérico, prefijo y tipo de unidad desde la PWA, y poder configurar los parámetros de distribución de mi organización (como el límite máximo de unidades por solicitud),  
**Para** configurar rápidamente la estructura de viviendas de mi propiedad horizontal sin crear unidades una por una, optimizando el proceso de puesta en marcha post-onboarding.

## Descripción

Se requiere implementar dos funcionalidades relacionadas en la PWA atlas-platform:

1. **Pantalla de generación masiva de unidades:** Accesible desde una nueva opción "Unidades" en el menú inferior de navegación del administrador. El formulario permite al admin especificar prefijo, rango numérico (mín/máx), tipo de unidad (APARTMENT/HOUSE), y opciones de vehículos (habilitados + límite). El frontend consume el endpoint existente `POST /api/units/distribute` del backend Atlas. El resultado muestra un resumen de unidades creadas vs. rechazadas (duplicadas) con detalle.

2. **Configuración de organización:** Formulario para parametrizar valores de la organización, entre ellos el límite máximo de unidades por distribución (por defecto: 100). Esto requiere persistencia en backend con un campo o tabla de configuración a nivel de organización, una migración de base de datos para agregar la estructura necesaria, y un formulario frontend para que el admin pueda editar estos parámetros.

El backend de distribución masiva ya existe y es funcional (`POST /api/units/distribute`). Esta historia se enfoca en: (a) el frontend que lo consume, (b) la configuración organizacional que define los límites, y (c) las validaciones frontend necesarias.

## Criterios de Aceptación

### Escenario 1: Generación masiva exitosa de unidades

- **Dado** que el administrador `ADMIN_ATLAS` está en la pantalla "Unidades" y tiene su organización activa
- **Cuando** completa el formulario con prefijo (ej. "A-"), rango mínimo (ej. 1), rango máximo (ej. 18), tipo de unidad "APARTMENT", habilita vehículos con límite 2, y presiona "Generar"
- **Entonces** el sistema envía la solicitud a `POST /api/units/distribute` con el `organizationId` del admin autenticado, crea las unidades dentro de su organización, y muestra un mensaje de éxito: "Se crearon 18 unidades exitosamente (A-1 a A-18)" con el conteo de creadas

### Escenario 2: Todas las unidades son duplicadas — cero creadas

- **Dado** que el administrador intenta generar unidades con un rango y prefijo donde TODAS las combinaciones ya existen en su organización
- **Cuando** envía la solicitud de distribución
- **Entonces** el sistema NO crea ninguna unidad y muestra un mensaje de advertencia: "No se crearon unidades. Todas las unidades del rango especificado ya existen en tu organización (18 rechazadas por duplicado)"

### Escenario 3: Creación parcial con duplicados

- **Dado** que el administrador genera unidades con un rango donde algunas ya existen (ej. A-1 a A-5 ya existen, A-6 a A-18 no)
- **Cuando** envía la solicitud de distribución
- **Entonces** el sistema crea solo las unidades nuevas y muestra un resumen: "Creadas: 13 | Rechazadas: 5 (duplicadas)" junto con una tabla de las unidades rechazadas mostrando el código de cada una y el motivo "Ya existe"

### Escenario 4: Validación — Rango mínimo mayor que máximo

- **Dado** que el administrador está en el formulario de generación masiva
- **Cuando** ingresa un rango mínimo mayor al rango máximo (ej. mín: 20, máx: 5)
- **Entonces** el sistema muestra una validación en tiempo real: "El rango mínimo debe ser menor o igual al rango máximo" y el botón "Generar" permanece deshabilitado

### Escenario 5: Validación — Rango excede límite configurado de la organización

- **Dado** que la organización del administrador tiene configurado un límite máximo de unidades por distribución (ej. 100 por defecto)
- **Cuando** el administrador ingresa un rango que generaría más unidades que el límite (ej. rango 1 a 150 = 150 unidades)
- **Entonces** el sistema muestra una validación: "El rango solicitado genera 150 unidades, pero el límite máximo configurado para tu organización es 100. Reduce el rango o ajusta la configuración" y el botón "Generar" permanece deshabilitado

### Escenario 6: Selector de tipo de unidad

- **Dado** que el administrador está en el formulario de generación masiva
- **Cuando** interactúa con el campo de tipo de unidad
- **Entonces** se muestra un selector con las opciones: "Apartamento" (APARTMENT) y "Casa" (HOUSE), y el valor seleccionado se envía al backend como `unitType`

### Escenario 7: Campos de vehículos en el formulario

- **Dado** que el administrador está en el formulario de generación masiva
- **Cuando** activa el checkbox "Habilitar vehículos"
- **Entonces** se muestra y habilita el campo "Límite de vehículos por unidad" (número, mínimo 1), y ambos valores se envían al backend como `vehiclesEnabled: true` y `vehicleLimit: N`. Si el checkbox está desactivado, se envía `vehiclesEnabled: false` y el campo de límite permanece oculto

### Escenario 8: Navegación al módulo de unidades desde menú inferior

- **Dado** que el administrador `ADMIN_ATLAS` está autenticado en la PWA con estado `ACTIVE`
- **Cuando** selecciona la opción "Unidades" en el menú inferior de navegación
- **Entonces** se muestra la pantalla de generación masiva de unidades con el formulario completo, respetando los estilos y colores del design system existente

### Escenario 9: Configuración de organización — Visualización y edición de parámetros

- **Dado** que el administrador `ADMIN_ATLAS` accede a la sección de configuración de su organización
- **Cuando** visualiza los parámetros configurables
- **Entonces** se muestran los campos editables incluyendo: "Límite máximo de unidades por distribución" (número), y el administrador puede modificar el valor y guardar los cambios con un mensaje de confirmación: "Configuración actualizada exitosamente"

### Escenario 10: Configuración de organización — Valor por defecto en nueva organización

- **Dado** que la organización fue creada recientemente durante el onboarding y no tiene configuración personalizada
- **Cuando** el sistema consulta el límite máximo de distribución para validar el formulario de unidades
- **Entonces** se utiliza el valor por defecto de 100 unidades máximas por solicitud de distribución

### Escenario 11: Error de conexión o servidor

- **Dado** que el administrador envía una solicitud de distribución masiva o intenta guardar la configuración
- **Cuando** el backend no está disponible o retorna un error de servidor
- **Entonces** el sistema muestra un mensaje de error: "No se pudo completar la operación. Verifica tu conexión e intenta nuevamente" y el formulario permanece habilitado para reintentar

## Información Recopilada

### Usuario y Contexto

- **Tipo de usuario:** Administrador de propiedad horizontal con rol `ADMIN_ATLAS` y permisos `UNITS_DISTRIBUTE`, `UNITS_CREATE`
- **Permisos requeridos:** `UNITS_DISTRIBUTE` (presente en JWT del usuario autenticado). Multi-tenant estricto: solo opera dentro de su organización
- **Valor de negocio:** Permitir la configuración rápida de las unidades habitacionales de la propiedad horizontal post-onboarding, evitando la creación manual una por una y reduciendo drásticamente el tiempo de puesta en marcha del sistema

### Reglas de Negocio

1. **Multi-tenant estricto:** Las unidades se crean exclusivamente dentro de la organización del administrador autenticado. El `organizationId` se obtiene del contexto de autenticación, no del formulario
2. **Idempotencia / duplicados:** Si una unidad ya existe (por `organizationId` + código generado), el endpoint la omite y la retorna como "rechazada". No se produce error de sistema, solo un conteo separado de creadas vs. rechazadas
3. **Límite configurable por organización:** El máximo de unidades por solicitud de distribución es configurable a nivel de organización. Valor por defecto: 100. Debe persistirse en base de datos con una tabla o campo de configuración. Requiere migración de BD
4. **Validación de rango:** `rangeStart` debe ser menor o igual a `rangeEnd`
5. **Tipo de unidad seleccionable:** El administrador elige explícitamente el tipo (APARTMENT o HOUSE) desde un selector visible en el formulario
6. **Vehículos parametrizables:** El administrador puede habilitar/deshabilitar vehículos y establecer el límite por unidad directamente desde el formulario de distribución
7. **Torre/Zona no aplican por ahora:** No se vinculan torres ni zonas en la distribución masiva. Estos campos se omiten del formulario en esta versión
8. **Prefijo libre:** Sin restricciones de longitud ni caracteres especiales en el prefijo
9. **Auditoría:** El backend registra la acción "BULK_UNITS_CREATED" con conteos de creadas y rechazadas (ya implementado en endpoint existente)

### Interfaz

- **Menú inferior:** Nueva opción "Unidades" visible para usuarios con rol `ADMIN_ATLAS`
- **Pantalla "Generar Unidades Masivas":** Formulario con campos: Prefijo (texto), Rango mínimo (número), Rango máximo (número), Tipo de unidad (selector: Apartamento/Casa), Habilitar vehículos (checkbox), Límite de vehículos (número, visible solo si checkbox activo). Botón principal: "Generar"
- **Resultado de distribución:** Resumen visible con conteo "Creadas: X | Rechazadas: Y". Si hay rechazadas, mostrar tabla con detalle (código de unidad + motivo de rechazo)
- **Configuración de organización:** Formulario accesible al admin para editar parámetros organizacionales, incluyendo el límite máximo de distribución. Debe contar con botón "Guardar" y mensaje de confirmación
- **Diseño:** Respetar design system existente (gradientes, tokens CSS, colores primarios, tipografía, componentes Atomic Design)

### Sistemas Externos

- No se integran sistemas externos adicionales. Todo se resuelve contra el backend Atlas existente (`POST /api/units/distribute` para distribución masiva)

## Contexto y Referencias

**Arquitectura:** Backend ya cuenta con endpoint funcional `POST /api/units/distribute` implementado en `UnitDistributionUseCase` / `UnitDistributionHandler` / `UnitDistributionRouterRest`. El modelo `Organization` tiene un campo `settings` (JSON) que podría aprovecharse para almacenar la configuración parametrizable. Documentación multitenant en `SISTEMA_MULTI_TENANT_DESIGN.md`.

**Historias relacionadas:** HU #1 (Login Multitenant PWA) — patrones de autenticación y environments. HU #2 (Flujo de Creación, Activación y Onboarding de Administradores) — creación de organización y onboarding del admin.

**Lecciones aprendidas:** 
- El endpoint `POST /api/units/distribute` ya existe y maneja duplicados retornándolos como "rejected" — reutilizar sin modificar el contrato existente
- Patrones de Atomic Design y Clean Architecture ya establecidos en HU #1 y #2 — seguir mismos patrones para nuevos componentes
- La validación del rango vs. límite configurado se realiza en frontend antes de enviar, consultando la configuración de la organización
- Los componentes `FormFieldComponent`, `TextInputComponent`, `ButtonComponent`, `SelectComponent` del design system existente deben reutilizarse

### Decisiones de Diseño

**Patrón Arquitectónico:** Clean Architecture (Bancolombia) + Atomic Design

**Justificación:** Mantener coherencia total con la arquitectura consolidada en HU #1 y #2. El frontend usa `Gateway → Adapter` con `Result<T>`, componentes Atomic Design reutilizables, path aliases y lazy loading. El backend implementa la capa completa Router → Handler → UseCase → Repository con R2DBC reactivo. La consistencia arquitectónica reduce la curva de aprendizaje y maximiza la reutilización de componentes existentes.

**Componentes Afectados:**

**Backend — Modificaciones (5):**

- **UnitDistributionUseCase (Modificación — Crítico):** Cambiar de "fallo total por duplicados" a "creación parcial": filtrar códigos existentes, crear solo los nuevos, retornar `UnitDistributionResult` con conteos `created` + `rejected` + detalle de rechazados.
  - Especificaciones: Nuevo método o refactorización de `createByDistribution()`. Usa `findByOrganizationIdAndCodeIn()` para identificar existentes, filtra lista de `buildUnits()`, persiste solo los nuevos con `saveAll()`. Retorna `UnitDistributionResult` en lugar de `Flux<Unit>`.
- **UnitDistributionHandler (Modificación — Mayor):** Obtener `organizationId` de `TenantContext` (no del request body). Mapear nuevo `UnitDistributionResult` al response con `createdCount`, `rejectedCount`, `rejectedDetails`.
  - Especificaciones: Reemplazar `req.getOrganizationId()` por `TenantContext.getOrganizationIdOrThrow()`. Adaptar mapeo a `UnitDistributionResponse` con nuevos campos.
- **UnitDistributionResponse (Modificación — Menor):** Agregar campos `rejectedCount: int` y `rejectedUnits: List<RejectedUnit>` (código + motivo de rechazo).
- **Organization (Modificación — Menor):** Agregar método `getMaxUnitsPerDistribution()` que parsea el campo `settings` (JSON String) y retorna el valor entero (default 100 si no existe o es inválido).
  - Especificaciones: Usa `com.fasterxml.jackson.databind.ObjectMapper` para parseo JSON. `try-catch` con fallback al default.
- **UnitDistributionValidator (Modificación — Menor):** Agregar validación `validateMaxDistributionLimit(int unitCount, int maxAllowed)` que lanza `BusinessException` si `unitCount > maxAllowed`.

### Validación de Impacto

**Hallazgos críticos de la validación técnica (Step 1.5):**

1. **Backend NO soporta creación parcial (CRÍTICO):** `UnitDistributionUseCase.createByDistribution()` lanza `DuplicateException` si CUALQUIER código ya existe (líneas 103-110). Los Escenarios 2 y 3 de la HU requieren creación parcial con reporte de duplicados. Requiere refactorización del flujo de duplicados.
2. **No existe validación de límite máximo (ALTO):** Ni `UnitDistributionValidator` ni el UseCase validan contra `Organization.settings.maxUnitsPerDistribution`. El Escenario 5 lo requiere.
3. **`organizationId` viene del request body (ALTO):** El Handler toma `req.getOrganizationId()` del body (línea 63). La HU exige multi-tenant estricto desde el contexto de autenticación (`TenantContext`).
4. **`AuthUser` frontend no tiene `organizationId` (MEDIO):** Necesario para el frontend. Se agrega como campo opcional.
5. **`BottomNavComponent` no es role-aware (MEDIO):** Items hardcoded por índice sin filtrar por rol. Se crea `AdminBottomNavComponent` separado (no se modifica el existente) siguiendo el precedente de `DoormanBottomNavComponent`.
6. **`saveAll()` no es batch real (BAJO):** `UnitRepositoryAdapter.saveAll()` hace inserts secuenciales con `flatMap(this::save)`. Aceptable para rangos ≤100, pero a futuro podría optimizarse con batch SQL.

**Análisis de dependencias:** Los cambios backend (Hitos 1-5) y frontend domain (Hitos 6-8) son independientes y pueden desarrollarse en paralelo. La integración ocurre en los Hitos 10-12.

**Impacto en consumidores:** La modificación del response de `POST /api/units/distribute` agrega campos nuevos (`rejectedCount`, `rejectedUnits`) sin remover los existentes — **retrocompatible**. El bulk-upload (`POST /api/units/bulk-upload/*`) no se ve afectado.

### Notas Técnicas

- **Componentes reutilizados del Design System:** `TextInputComponent`, `SelectInputComponent`, `CheckboxInputComponent`, `ButtonComponent`, `FormFieldComponent`. NO crear componentes nuevos para estos elementos.
- **Patrón `Result<T>`:** Obligatorio en todos los gateways y use cases frontend. Usar factorías `success()` y `failure()` de `api-response.model.ts`.
- **Componentes locales vs generales:** `BulkUnitFormComponent` y `DistributionResultComponent` son **locales a la página** (en `pages/admin/units/components/`). `AdminBottomNavComponent` es **general** (en `ui/organisms/`).
- **Owner no aplica:** El Handler ya hardcodea `owner(null)` y `sendInvitationImmediately(false)` — no se toca este flujo.
- **Parseo de `Organization.settings`:** Usar Jackson `ObjectMapper` con `try-catch`. Si el JSON es null, vacío o no tiene la clave, retornar defaults. NO crear tabla separada — el campo `settings JSON NULL` ya existe en V1.
- **Migración V11:** Puede ser un `ALTER` que setee un `DEFAULT` al campo `settings`, o simplemente un `INSERT/UPDATE` para organizaciones existentes. El campo ya existe como `JSON NULL`.

Backend: refactorización CRÍTICA del `UnitDistributionUseCase` (all-or-nothing → creación parcial), corrección de seguridad multi-tenant (organizationId desde TenantContext), nuevo dominio de configuración de organización (UseCase + Handler + Router), migración V13, y modelo de value objects nuevos (`UnitDistributionResult`, `RejectedUnit`, `OrganizationSettings`). Frontend: 2 páginas nuevas (generación masiva + configuración org), 3 organisms (formulario bulk, resultado distribución, admin bottom nav), 2 gateways + 2 adapters, 3 use cases, y extensión de `AuthUser`. La complejidad se eleva por la refactorización de lógica backend existente (cambio de contrato de retorno de `Flux<Unit>` a `Mono<UnitDistributionResult>`) y por los 6 hallazgos del arquitecto que requieren correcciones de seguridad y funcionalidad.

**Riesgos técnicos conocidos:**
1. **Refactorización de contrato UseCase (CRÍTICO):** `createByDistribution()` actualmente retorna `Flux<Unit>`. Debe cambiar a `Mono<UnitDistributionResult>`. El Handler y cualquier otro consumidor del UseCase deben adaptarse al nuevo tipo de retorno. Riesgo de romper el endpoint `bulk-upload` si comparte lógica.
2. **Seguridad multi-tenant:** El Handler actual acepta `organizationId` del request body sin verificación. Al migrar a `TenantContext`, el `TenantFilter` debe estar configurado correctamente para poblar el contexto antes de que llegue al Handler. Verificar que `TenantFilter` extrae org del JWT.
3. **Parseo JSON de `settings`:** El campo `settings` es `String` (JSON) en `Organization.java`. Parsear con Jackson requiere manejar: null, string vacío, JSON malformado, clave ausente. Fallback a defaults obligatorio.
4. **`saveAll()` secuencial:** `UnitRepositoryAdapter.saveAll()` hace inserts uno a uno con `flatMap(this::save)`. Para rangos ≤100 es aceptable, pero si el admin configura un límite mayor, podría haber latencia. Documentar como deuda técnica.
5. **Migración V13:** La última migración es V12. La nueva V13 debe actualizar organizaciones existentes con settings por defecto sin afectar datos existentes en el campo `settings` si ya tuvieran contenido.
6. **Sin tests existentes para `UnitDistributionUseCase`:** No hay tests unitarios ni de integración para el use case que se va a refactorizar. Alto riesgo de regresión — es imperativo crear tests ANTES de refactorizar.

**Patrones y convenciones del equipo:**
- **Backend:** Clean Architecture Bancolombia (Router → Handler → UseCase → Repository), Spring WebFlux/Reactor (`Mono<T>`/`Flux<T>`), inner records para commands/results, validación en use cases con `System.Logger`, `@RequiredArgsConstructor` para DI
- **Frontend:** Clean Architecture (domain/models → domain/gateways → domain/use-cases → infrastructure/adapters → presentation), Atomic Design, `Result<T>` con factorías `success()`/`failure()`, componentes standalone + OnPush + signals
- **Guards:** `CanActivateFn` con `inject()` (no clases)
- **Componentes locales:** Organisms específicos de una página van en `pages/[page]/components/organisms/` — no en `ui/organisms/`
- **Componentes generales:** Organisms reutilizables entre páginas van en `ui/organisms/`
- **BottomNav:** Componentes separados por rol (precedente: `BottomNavComponent` para residentes, `DoormanBottomNavComponent` para porteros → `AdminBottomNavComponent` para admins)
- **Path aliases:** `@domain/`, `@infrastructure/`, `@presentation/`, `@env/`
- **Naming backend:** value objects como records, DTOs con sufijo Request/Response, handlers con sufijo Handler

**Dependencias nuevas a instalar:**
Ninguna — todas las dependencias necesarias ya están en el proyecto (Jackson ObjectMapper ya disponible en Spring Boot, Angular HttpClient, ReactiveFormsModule, Jasmine+Karma, JUnit 5+Reactor Test)

**Estrategia de testing:**
Frontend: Jasmine + Karma (`describe/it/expect`, `jasmine.createSpyObj()` para mocks, `ComponentFixture` para componentes) | Backend: JUnit 5 + Reactor Test (`StepVerifier`), WebTestClient para integración, AssertJ para aserciones | Tests requeridos: BE → tests unitarios para `UnitDistributionUseCase` refactorizado (creación parcial, duplicados, límite max), `OrganizationSettingsUseCase`, `Organization.getMaxUnitsPerDistribution()`, `UnitDistributionValidator` (límite max); FE → spec para cada page, organism, guard, adapter y use-case | Cobertura: ≥70% líneas (JaCoCo BE), best-effort FE | Builders: No existen — crear `UnitDistributionBuilder` y `OrganizationBuilder` para tests de backend
