# Historia #4: Creación de Portero (Gatekeeper)

**Estado:** Implementado (Developer) - Pendiente Peer Review

---

## Historia de Usuario

**Como** administrador con rol `ADMIN_ATLAS` de una organización activa en la plataforma ATLAS,  
**Quiero** crear usuarios de tipo Portero desde la vista de gestión de porteros, seleccionando el tipo de portero (general o delivery) y generando una URL de enrolamiento con token de un solo uso,  
**Para** habilitar dispositivos dedicados de portería que puedan validar autorizaciones de ingreso en mi propiedad horizontal.

## Descripción

Se requiere implementar la funcionalidad de creación de porteros desde la PWA atlas-platform. El administrador (`ADMIN_ATLAS`) podrá acceder a una vista "Gestión de Porteros" donde verá la lista de porteros existentes de su organización y podrá crear nuevos porteros. Al crear un portero, el sistema genera un usuario con estado inicial (`RECEIVED` o `CREATED` según la state machine existente), le asigna roles y permisos de portería, y genera una URL de enrolamiento con un token de un solo uso con expiración de 24 horas. Esta URL se entrega al administrador para que la abra en el dispositivo dedicado de portería (paso cubierto en HU #5). Los porteros quedan asociados a la organización del administrador bajo el esquema multi-tenant estricto.

## Criterios de Aceptación

### Escenario 1: Creación exitosa de un portero general

- **Dado** que el administrador `ADMIN_ATLAS` está en la vista "Gestión de Porteros" y su organización está activa
- **Cuando** presiona "Crear Portero", selecciona tipo `PORTERO_GENERAL`, ingresa un nombre descriptivo (ej. "Portería Principal") y confirma la creación
- **Entonces** el sistema crea un usuario portero con estado inicial, le asigna los permisos de portería (`AUTHORIZATIONS_VALIDATE`, `ACCESS_LOG_CREATE`, `ACCESS_LOG_READ_OWN_ORG`, `VEHICLES_VALIDATE`), genera una URL de enrolamiento con token de 24 horas de un solo uso, y muestra la URL al administrador con opciones para copiarla

### Escenario 2: Creación exitosa de un portero delivery

- **Dado** que el administrador `ADMIN_ATLAS` está en la vista "Gestión de Porteros"
- **Cuando** crea un portero de tipo `PORTERO_DELIVERY` con nombre descriptivo (ej. "Portería Delivery")
- **Entonces** el sistema crea el portero con el tipo `PORTERO_DELIVERY` y los mismos permisos base, genera la URL de enrolamiento, y lo muestra en la lista de porteros con su tipo diferenciado

### Escenario 3: Lista de porteros existentes

- **Dado** que el administrador `ADMIN_ATLAS` accede a la vista "Gestión de Porteros"
- **Cuando** se carga la pantalla
- **Entonces** se muestra una lista con todos los porteros de su organización, mostrando para cada uno: nombre, tipo (General/Delivery), estado (Pendiente de enrolamiento / Activo / Inactivo), último acceso, y dispositivo enlazado (si aplica)

### Escenario 4: Validación de campos obligatorios

- **Dado** que el administrador está en el formulario de creación de portero
- **Cuando** intenta crear un portero sin completar el nombre descriptivo o sin seleccionar el tipo de portero
- **Entonces** el sistema muestra mensajes de validación en los campos faltantes: "Este campo es obligatorio" y el botón de creación permanece deshabilitado

### Escenario 5: URL de enrolamiento generada con token single-use

- **Dado** que un portero acaba de ser creado exitosamente
- **Cuando** el sistema muestra la URL de enrolamiento
- **Entonces** la URL contiene un token único con expiración de 24 horas, se muestra con un botón "Copiar URL" para facilitar su distribución, y se advierte al administrador: "Esta URL es de un solo uso y expira en 24 horas"

### Escenario 6: Regenerar URL de enrolamiento

- **Dado** que existe un portero cuyo token de enrolamiento expiró o no fue utilizado
- **Cuando** el administrador selecciona la opción "Regenerar URL" para ese portero
- **Entonces** el sistema invalida el token anterior, genera un nuevo token con 24 horas de expiración, y muestra la nueva URL de enrolamiento

### Escenario 7: Error de conexión al crear portero

- **Dado** que el administrador completa el formulario de creación de portero
- **Cuando** el backend no está disponible o retorna un error de servidor
- **Entonces** el sistema muestra un mensaje de error: "No se pudo crear el portero. Verifica tu conexión e intenta nuevamente" y el formulario permanece habilitado para reintentar

## Información Recopilada

### Usuario y Contexto

- **Tipo de usuario:** Administrador de propiedad horizontal con rol `ADMIN_ATLAS`
- **Permisos requeridos:** Permisos de gestión de porteros (crear, listar, gestionar porteros dentro de su organización)
- **Valor de negocio:** Habilitar la creación de cuentas de portero que posteriormente se enrolarán en dispositivos dedicados para validar el ingreso de personas y vehículos a la propiedad horizontal

### Reglas de Negocio

1. **Multi-tenant estricto:** El portero creado queda asociado al `organizationId` del administrador que lo crea. No hay acceso cruzado entre organizaciones
2. **Token single-use con expiración 24h:** El token de enrolamiento `PORTER_ENROLL_TOKEN` solo puede usarse una vez. Al consumirse se marca como utilizado. Si expira, el admin puede regenerarlo
3. **Tipos de portero extensibles:** Inicialmente `PORTERO_GENERAL` (cualquier portero puede usarlo para validar autorizaciones y habilitar paso) y `PORTERO_DELIVERY` (cuando un repartidor o delivery desea registrarse y validar desde su dispositivo). El sistema debe ser extensible para futuros tipos
4. **Permisos asignados al portero:** `AUTHORIZATIONS_VALIDATE`, `ACCESS_LOG_CREATE`, `ACCESS_LOG_READ_OWN_ORG`, `VEHICLES_VALIDATE`
5. **Auditoría obligatoria:** Registrar eventos `PORTER_CREATED` y `PORTER_ENROLL_URL_GENERATED` con datos del administrador que ejecutó la acción

### Interfaz

- **Ubicación en navegación:** La opción "Portería" aparece en el menú inferior **solo para usuarios con rol de portero**. La vista de "Gestión de Porteros" es accesible para el `ADMIN_ATLAS` desde su panel de administración
- **Vista "Gestión de Porteros":** Lista de porteros con columnas (nombre, tipo, estado, último acceso, dispositivo enlazado). Botón "Crear Portero" prominente
- **Formulario de creación:** Campos: Nombre descriptivo (texto), Tipo de portero (selector: General / Delivery). Botón "Crear"
- **Post-creación:** Mostrar URL generada con botón "Copiar URL" y advertencia de expiración
- **Diseño:** Respetar design system existente (gradientes, tokens CSS, Atomic Design)

### Sistemas Externos

- No se integran sistemas externos adicionales. Todo se resuelve contra el backend Atlas

## Contexto y Referencias

**Arquitectura:** Backend reactivo con WebFlux. Clean Architecture con UseCases separados. Patrón de tokens single-use ya implementado en HU #2 (activación de admin). Modelo multi-tenant con `organizationId` en todo.

**Historias relacionadas:** HU #1 (Login Multitenant PWA) — patrones de autenticación y JWT. HU #2 (Creación, Activación y Onboarding de Administradores) — patrón de token single-use 24h reutilizable. HU #5 (Enrolamiento Dispositivo Portería) — consume la URL generada aquí.

**Lecciones aprendidas:**
- El flujo de token de activación de HU #2 sirve como patrón para el token de enrolamiento de portero
- Los roles y permisos se asignan en el JWT tras autenticación — seguir mismo patrón para permisos de portero
- Mantener la nomenclatura de estados de la state machine existente (`RECEIVED`, `CREATED`, `ACTIVATED`, `ACTIVE`)

### Decisiones de Diseño

**Patrón Arquitectónico:** Clean Architecture (Bancolombia) + Atomic Design

**Justificación:** Mantener coherencia total con la arquitectura consolidada en HU #1, #2 y #3. El backend sigue el scaffold Clean Architecture de Bancolombia (Router → Handler → UseCase → Repository) con WebFlux/R2DBC reactivo. El frontend usa `Gateway → Adapter` con `Result<T>`, componentes Atomic Design, path aliases y standalone components con signals. ### Validación de Impacto

**Hallazgos críticos de la validación técnica (Step 1.5):**

1. **`users.email` es NOT NULL UNIQUE (CRÍTICO):** La tabla `users` tiene constraint `email VARCHAR(160) NOT NULL UNIQUE` (migración V1). Los porteros son dispositivos, no personas con email. Solución: Email sintético `porter-{uuid}@{org-slug}.atlas.internal` que cumple el constraint sin colisionar con emails reales.
2. **Roles y permisos de portero NO existen en BD (CRÍTICO):** Los roles `PORTERO_GENERAL` y `PORTERO_DELIVERY` no existen en `roles`. Los permisos `AUTHORIZATIONS_VALIDATE`, `ACCESS_LOG_CREATE`, `ACCESS_LOG_READ_OWN_ORG`, `VEHICLES_VALIDATE` no existen en `permissions`. Solución: Migración V13 con INSERT de roles, permisos y relaciones `role_permissions`.
3. **`UserStatus` no tiene estados RECEIVED/CREATED (ALTO):** La historia menciona estados `RECEIVED`/`CREATED` pero el enum `UserStatus.java` solo tiene: `ACTIVE`, `PRE_REGISTERED`, `PENDING_ACTIVATION`, `ACTIVATED`, `SUSPENDED`. Solución: Mapeo semántico — `PRE_REGISTERED` = pendiente de enrolamiento, `ACTIVATED` = post-enrolamiento, `ACTIVE` = activo completo.
4. **`JwtTokenAdapter.calculateDefaultRoute()` no tiene routing para portero (ALTO):** Solo existe `SECURITY → /access-control`. No hay cases para `PORTERO_*`. Solución: Agregar cases para `PORTERO_GENERAL` y `PORTERO_DELIVERY` → `/entry-control`.
5. **`AdminActivationToken` tiene `initialPasswordHash` que NO aplica a porteros (ALTO):** El token de admin incluye BCrypt hash de contraseña inicial — los porteros se enrolan como dispositivos sin password. Solución: Crear modelo dedicado `PorterEnrollmentToken` sin ese campo.
6. **`AdminBottomNavComponent` NO existe aún (MEDIO):** Propuesto en HU #3 pero no implementado. El componente se necesita para la navegación del admin. Solución: Crear como parte de esta HU (o HU #3, la primera que se implemente).
7. **No existe utilidad de clipboard en el proyecto (MEDIO):** Para el botón "Copiar URL" se necesita `navigator.clipboard.writeText()`. No hay wrapper existente. Solución: Usar API nativa directamente en `EnrollmentUrlComponent` con fallback `document.execCommand('copy')`.
8. **Código completamente greenfield (BAJO):** No existe ningún código de portero en backend ni frontend. Todo es nuevo, sin riesgo de regresión. Ventaja: diseño limpio sin deuda técnica heredada.

**Análisis de dependencias:** Los cambios backend (Hitos 1-7) y frontend domain/infra (Hitos 8-9) son independientes y pueden desarrollarse en paralelo. La integración ocurre en el Hito 10.

**Impacto en consumidores:** Todos los endpoints son nuevos (`POST /api/porters`, `GET /api/porters`, `POST /api/porters/{id}/regenerate-url`). No hay impacto en APIs existentes. La migración V13 agrega tablas y datos semilla sin alterar estructuras existentes — sin riesgo de regresión.

**Contratos API:**
- `POST /api/porters` → Request: `{ displayName: string, porterType: "PORTERO_GENERAL" | "PORTERO_DELIVERY" }` → Response: `{ porter: Porter, enrollmentUrl: string }` (201 Created)
- `GET /api/porters` → Response: `{ porters: Porter[] }` (200 OK)
- `POST /api/porters/{id}/regenerate-url` → Response: `{ enrollmentUrl: string }` (200 OK)

### Notas Técnicas

- **Decisión: `PorterEnrollmentToken` vs reutilizar `AdminActivationToken`:** Se descarta reutilizar `AdminActivationToken` con discriminador porque: (1) `AdminActivationToken` tiene `initialPasswordHash` (BCrypt) que no aplica a dispositivos, (2) la semántica es diferente (activación personal vs enrolamiento de dispositivo), (3) un modelo dedicado es más limpio y evita campos nullable innecesarios.
- **Email sintético:** Patrón `porter-{uuid}@{org-slug}.atlas.internal`. El UUID viene de `java.util.UUID.randomUUID()`. El `org-slug` se obtiene del campo `slug` de la organización (o `organizationId` si no existe slug). El dominio `.atlas.internal` es un TLD que no existe en internet y no recibe correo.
- **Mapeo de estados de portero:** Frontend muestra `PENDING_ENROLLMENT` (= `PRE_REGISTERED` en BD), `ACTIVE` (= `ACTIVE` en BD), `INACTIVE` (= `SUSPENDED` en BD). El mapeo se hace en el adapter frontend.
- **Componentes reutilizados del Design System:** `TextInputComponent`, `SelectInputComponent`, `ButtonComponent`. NO crear componentes nuevos para estos elementos.
- **Patrón `Result<T>`:** Obligatorio en todos los gateways y use cases frontend. Usar factorías `success()` y `failure()` de `api-response.model.ts`.
- **Componentes locales vs generales:** `PorterListComponent`, `PorterCreateFormComponent` y `EnrollmentUrlComponent` son **locales a la página** (en `pages/admin/porters/components/`). `AdminBottomNavComponent` es **general** (en `ui/organisms/`).

- **Guards:** `CanActivateFn` con `inject()` (no clases)
- **Componentes locales:** Organisms específicos de página en `pages/[page]/components/organisms/`
- **Componentes generales:** `ui/organisms/` (ej: `DoormanBottomNavComponent`, `BottomNavComponent`)
