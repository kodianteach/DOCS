# Historia #5: Enrolamiento del Dispositivo de Portería

**Estado:** ✅ Implementación Completada (Developer) — Pendiente Peer Review + QA Manual

---

## Historia de Usuario

**Como** dispositivo de portería al que se le asignó una URL de enrolamiento generada por el administrador,  
**Quiero** abrir la URL, instalar la PWA, y descargar la clave criptográfica de verificación de la organización durante el proceso de enrolamiento,  
**Para** quedar configurado como punto de validación de autorizaciones de ingreso capaz de funcionar incluso sin conexión a internet.

## Descripción

Se requiere implementar el flujo de enrolamiento de un dispositivo de portería. Cuando el administrador crea un portero (HU #4), se genera una URL con token de un solo uso. Al abrir esta URL en un dispositivo dedicado (tablet, celular de portería), el sistema valida el token, guía la instalación de la PWA, y completa el enrolamiento descargando e instalando localmente la clave pública de verificación criptográfica de la organización. Esta clave permite al dispositivo validar QRs de autorizaciones offline verificando la firma digital sin necesidad de conexión al servidor. El material criptográfico se almacena en storage seguro dentro de la PWA (IndexedDB + WebCrypto API). Al completar el enrolamiento, el token se marca como consumido y el portero pasa a estado activo.

## Criterios de Aceptación

### Escenario 1: Apertura de URL con token válido

- **Dado** que el administrador generó una URL de enrolamiento para un portero y el token no ha expirado ni sido consumido
- **Cuando** se abre la URL en el dispositivo de portería
- **Entonces** el sistema valida el token contra el backend, confirma que es válido, y muestra una pantalla de bienvenida con instrucciones para instalar la PWA: "Instala la aplicación Atlas Portería" con botón de instalación e instrucciones de "Agregar a pantalla de inicio"

### Escenario 2: Token inválido o expirado

- **Dado** que se abre una URL de enrolamiento con un token que ya expiró, fue consumido, o es inválido
- **Cuando** el sistema valida el token
- **Entonces** se muestra un mensaje de error: "El enlace de enrolamiento es inválido o ha expirado. Solicita un nuevo enlace al administrador" y NO se muestra ningún formulario ni opción de instalación

### Escenario 3: Instalación exitosa de la PWA y enrolamiento completo

- **Dado** que el token fue validado exitosamente y el usuario presionó "Instalar aplicación"
- **Cuando** la PWA se instala en el dispositivo y se completa el proceso de enrolamiento
- **Entonces** el sistema envía la información del dispositivo (plataforma, modelo, versión de app) al backend, recibe la clave pública de verificación (`verificationKey`) y las reglas offline (`maxClockSkewMinutes`), almacena la clave en storage seguro (IndexedDB + WebCrypto), marca el token como consumido, cambia el estado del portero a activo, y muestra: "Dispositivo enrolado exitosamente. Listo para validar autorizaciones"

### Escenario 4: Almacenamiento de clave criptográfica en storage seguro

- **Dado** que el enrolamiento se completó exitosamente
- **Cuando** la PWA recibe la `verificationKey` (clave pública JWK con algoritmo EdDSA)
- **Entonces** la clave se almacena en IndexedDB utilizando WebCrypto API como `CryptoKey` no exportable, junto con el `kid` (key identifier) y las reglas de tolerancia de reloj (`maxClockSkewMinutes: 10`), garantizando que el material criptográfico persista entre reinicios de la aplicación

### Escenario 5: Dispositivo ya enrolado previamente

- **Dado** que un dispositivo ya fue enrolado con un portero
- **Cuando** se intenta abrir una nueva URL de enrolamiento en el mismo dispositivo
- **Entonces** el sistema detecta que ya existe un enrolamiento previo, muestra una advertencia: "Este dispositivo ya está enlazado al portero [nombre]. ¿Deseas reemplazar el enrolamiento anterior?" con opciones de confirmar o cancelar

### Escenario 6: Error de conexión durante enrolamiento

- **Dado** que el token fue validado y la PWA está instalada
- **Cuando** el proceso de enrolamiento falla por falta de conexión o error del servidor
- **Entonces** el sistema muestra un mensaje: "No se pudo completar el enrolamiento. Verifica tu conexión a internet e intenta nuevamente" y permite reintentar sin consumir el token

## Información Recopilada

### Usuario y Contexto

- **Tipo de usuario:** Dispositivo de portería operado por el administrador durante la configuración inicial. Posteriormente operado por el portero asignado
- **Permisos requeridos:** Token de enrolamiento válido generado por `ADMIN_ATLAS` (HU #4)
- **Valor de negocio:** Configurar dispositivos dedicados de portería con capacidad de validación offline de autorizaciones, eliminando la dependencia total de conectividad a internet para el control de acceso

### Reglas de Negocio

1. **Token single-use:** El token de enrolamiento se consume al completar el enrolamiento. No puede reutilizarse. Si falla el enrolamiento por error técnico, el token NO se consume para permitir reintento
2. **Clave criptográfica local:** La PWA almacena una clave pública (no privada) de verificación. El backend firma las autorizaciones con la clave privada; el dispositivo solo verifica firmas, nunca genera firmas
3. **Storage seguro:** Utilizar IndexedDB + WebCrypto API para almacenar la `CryptoKey` como no exportable. NO almacenar en localStorage ni como texto plano
4. **Reglas offline:** El servidor envía `maxClockSkewMinutes` (ej. 10 minutos) como tolerancia de reloj para validaciones offline. El dispositivo almacena esta configuración localmente
5. **Vinculación dispositivo-portero:** Cada dispositivo queda vinculado a un portero específico. Los datos del dispositivo (plataforma, modelo, versión) se registran en el backend
6. **Auditoría obligatoria:** Registrar evento `PORTER_DEVICE_ENROLLED` con datos del dispositivo, portero y organización
7. **Sincronización continua:** Una vez enrolado, el dispositivo debe **siempre intentar actualizarse del servidor** (claves actualizadas, lista de revocaciones, configuraciones). La app mantiene un proceso de sincronización periódica en segundo plano cuando hay conexión

### Interfaz

- **Pantalla de enrolamiento (URL con token):** Pantalla centrada con logo ATLAS, instrucciones de instalación PWA, botón "Instalar aplicación" que activa prompt nativo del navegador
- **Post-instalación:** Flujo guiado de enrolamiento automático tras instalar la PWA
- **Pantalla de éxito:** Confirmación visual de enrolamiento completado con nombre del portero y organización
- **Pantalla de error:** Mensajes claros para token inválido/expirado y errores de conexión

### Sistemas Externos

- No se integran sistemas externos. El enrolamiento se comunica con el backend Atlas. La PWA utiliza APIs del navegador (WebCrypto, IndexedDB, Service Worker)

---

## Contexto y Referencias

**Arquitectura:** PWA con Service Worker para funcionalidad offline. WebCrypto API para manejo de claves criptográficas. IndexedDB para persistencia local segura. Backend reactivo WebFlux.

**Historias relacionadas:** HU #2 (Flujo de Activación de Administradores) — patrón de token single-use y prompt de instalación PWA reutilizable. HU #4 (Creación de Portero) — genera la URL que este flujo consume. HU #7 (Validación en Portería) — usa la clave instalada aquí para verificar firmas offline.

**Lecciones aprendidas:**
- `PwaUpdateService` de HU #2 ya captura `beforeinstallprompt` y expone `promptInstall()` — reutilizar para la instalación PWA del portero
- El patrón de token single-use de HU #2 funciona correctamente y debe seguirse para el token de enrolamiento
- La clave criptográfica debe ser una clave pública en formato JWK (JSON Web Key) para compatibilidad con WebCrypto API

### Decisiones de Diseño

**Patrón Arquitectónico:** Clean Architecture (Bancolombia) + Atomic Design

**Justificación:** Coherencia total con HU #1–#4. El backend sigue el scaffold Clean Architecture (Router → Handler → UseCase → Repository) bajo `/api/external/porter/**` como endpoint público (ya `permitAll` en `SecurityConfig`). El frontend implementa un flujo de página pública (`/enroll/:token`) sin autenticación, reutilizando `PwaUpdateService.promptInstall()` existente, y añadiendo capacidades nuevas de **IndexedDB + WebCrypto API** para almacenamiento seguro de claves criptográficas. Se crea infraestructura criptográfica completa (generación EdDSA key pairs por organización, almacenamiento, entrega de public key JWK al dispositivo).

**Componentes Afectados:**

**Backend — Nuevos Domain (4):**

- **OrganizationCryptoKey (Nuevo — Domain Model):** Modelo para par de claves criptográficas por organización. Campos: `id`, `organizationId`, `keyType` (SIGNING/VERIFICATION), `algorithm` (EdDSA), `keyId` (kid, UUID), `publicKeyJwk` (TEXT, formato JWK), `privateKeyEncrypted` (TEXT, clave privada cifrada con master key), `isActive`, `createdAt`, `rotatedAt`. Métodos: `isActive()`, `getPublicKeyAsJwk()`. Ubicación: `domain/model/.../crypto/`.
  - Especificaciones: La clave privada se almacena cifrada con una master key definida en properties (AES-256). Solo el backend la descifra para firmar QRs (HU #7). El dispositivo solo recibe la clave pública.
- **CryptoKeyGateway (Nuevo — Gateway Interface):** `save(OrganizationCryptoKey) → Mono<OrganizationCryptoKey>`, `findActiveByOrganizationId(Long) → Mono<OrganizationCryptoKey>`, `findByKeyId(String kid) → Mono<OrganizationCryptoKey>`. Ubicación: `domain/model/.../crypto/gateway/`.
- **EnrollmentResult (Nuevo — Domain Model):** Value object para el resultado de enrolamiento. Campos: `porterId`, `porterDisplayName`, `organizationName`, `verificationKeyJwk` (String, public key en formato JWK), `keyId` (kid), `maxClockSkewMinutes` (Integer, default 10). Ubicación: `domain/model/.../porter/`.
- **DeviceInfo (Nuevo — Domain Model):** Value object con datos del dispositivo: `platform`, `model`, `appVersion`, `userAgent`. Ubicación: `domain/model/.../porter/`.

**Backend — Nuevos Use Cases (2):**

- **ValidateEnrollmentTokenUseCase (Nuevo — UseCase):** Valida token de enrolamiento sin consumirlo (paso 1 del flujo). Sigue el patrón exacto de `ActivateAdminUseCase.validateToken()`: (1) Hash SHA-256 del raw token, (2) Lookup por `tokenHash`, (3) Validar estado PENDING + no expirado, (4) Lookup porter + organization, (5) Retornar `EnrollmentTokenValidationResult` con `porterDisplayName`, `organizationName`, `expiresAt`, `valid`. Ubicación: `domain/usecase/.../porter/`.
  - Especificaciones: NO depende de `TenantContext` — resuelve `organizationId` a través del token → porter → user. JwtAuthFilter y TenantFilter ya saltan rutas `/api/external`.
- **EnrollPorterDeviceUseCase (Nuevo — UseCase):** Consume el token y completa el enrolamiento (paso 2). Flujo: (1) Valida token (mismo método), (2) Captura `DeviceInfo` del dispositivo, (3) Actualiza porter con `linkedDeviceId`, `linkedDeviceInfo`, (4) Cambia estado del usuario portero a `ACTIVE`, (5) Marca token como `CONSUMED`, (6) Obtiene `OrganizationCryptoKey` activa de la organización → Si no existe, genera par EdDSA (lazy generation), (7) Registra auditoría `PORTER_DEVICE_ENROLLED`, (8) Retorna `EnrollmentResult` con la clave pública JWK + `keyId` + `maxClockSkewMinutes`. Ubicación: `domain/usecase/.../porter/`.
  - Especificaciones: La generación de claves es "lazy" — se genera el par EdDSA la primera vez que un dispositivo se enrola en una organización. Usar `java.security.KeyPairGenerator` con `Ed25519` (nativo Java 21). Token solo se marca `CONSUMED` al final exitoso; si falla, el device puede reintentar.

**Backend — Nuevos Infrastructure (5):**

- **CryptoKeyRepositoryAdapter (Nuevo — R2DBC Adapter):** Implementa `CryptoKeyGateway` con R2DBC. Queries contra tabla `organization_crypto_keys`. Cifrado/descifrado de `privateKeyEncrypted` con AES-256 usando master key. Ubicación: `infrastructure/driven-adapters/.../crypto/`.
- **CryptoKeyGeneratorService (Nuevo — Helper/Service):** Servicio de generación de claves EdDSA. Métodos: `generateKeyPair() → KeyPair`, `exportPublicKeyAsJwk(PublicKey) → String`, `exportPrivateKeyEncrypted(PrivateKey, String masterKey) → String`, `decryptPrivateKey(String encrypted, String masterKey) → PrivateKey`. Usa `java.security.KeyPairGenerator.getInstance("Ed25519")` + Jackson para JWK format + AES-256 para cifrado. Ubicación: `infrastructure/helpers/.../crypto/`.
  - Especificaciones: Java 21 soporta Ed25519 nativamente. Formato JWK exportado: `{ "kty": "OKP", "crv": "Ed25519", "x": "<base64url-public-key>" }`. Cifrado de clave privada: AES/GCM/NoPadding con IV aleatorio.
- **ExternalPorterHandler (Nuevo — Handler):** Maneja requests de enrolamiento público. Métodos: `validateToken(ServerRequest)` → GET con `?token=`, `enroll(ServerRequest)` → POST con body `{token, deviceInfo}`. Sigue patrón exacto de `ExternalAdminHandler`. Extrae `clientIp` y `userAgent` de `ServerRequest` para auditoría. Ubicación: `infrastructure/entry-points/.../external/`.
- **ExternalPorterRouterRest (Nuevo — Router):** Rutas: `GET /api/external/porter/validate-token`, `POST /api/external/porter/enroll`. Documentado con `@RouterOperations` OpenAPI. Sigue patrón de `ExternalAdminRouterRest`. Ubicación: `infrastructure/entry-points/.../external/`.
- **Migración V14 (Nuevo — SQL):** Crea tabla `organization_crypto_keys` (id BIGINT AUTO_INCREMENT PK, organization_id BIGINT NOT NULL FK→organizations, algorithm VARCHAR(20) NOT NULL DEFAULT 'Ed25519', key_id VARCHAR(100) NOT NULL UNIQUE, public_key_jwk TEXT NOT NULL, private_key_encrypted TEXT NOT NULL, is_active BOOLEAN NOT NULL DEFAULT TRUE, created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP, rotated_at TIMESTAMP NULL). NOTA: V13 está reservada por HU #4 (tablas `porters`, `porter_enrollment_tokens`, roles, permisos).

- **crypto-storage.service.ts (Nuevo — Service):** Servicio para almacenamiento seguro de claves criptográficas. Métodos: `importAndStoreKey(jwk: JsonWebKey, kid: string): Promise<void>` — usa `crypto.subtle.importKey('jwk', jwk, {name: 'Ed25519'}, false, ['verify'])` con `extractable: false`, luego almacena `CryptoKey` en IndexedDB. `getKey(kid: string): Promise<CryptoKey | null>` — recupera la `CryptoKey` desde IndexedDB. `storeOfflineRules(rules: {maxClockSkewMinutes: number}): Promise<void>` — almacena reglas offline. `hasEnrollment(): Promise<boolean>` — verifica si ya existe un enrolamiento previo (Escenario 5). `clearEnrollment(): Promise<void>` — limpia datos de enrolamiento previo. ### Validación de Impacto

**Hallazgos críticos de la validación técnica (Step 1.5):**

1. **CERO infraestructura criptográfica en el backend (CRÍTICO):** No existe EdDSA, JWK, claves asimétricas ni tabla de claves en todo el proyecto. Grep para `crypto|EdDSA|JWK|public_key|verification_key|signing_key` retorna zero matches (solo `javax.crypto.SecretKey` para JWT HMAC y `BCryptPasswordEncoder`). Solución: Subsistema completo nuevo — modelo, tabla, servicio de generación, adapter.
2. **`Organization.java` NO tiene campos de claves (CRÍTICO):** Solo tiene: `id`, `companyId`, `code`, `name`, `slug`, `type`, `usesZones`, `allowedUnitTypes`, `description`, `settings` (JSON), `status`, `isActive`, timestamps. Sin `publicKey`, `verificationKey`, `signingKey`. Solución: Crear tabla separada `organization_crypto_keys` (soporta key rotation, separación de concerns, múltiples algoritmos a futuro).
3. **`SecurityConfig`: `/api/external/**` ya es `permitAll` (POSITIVO):** Verificado en SecurityConfig.java línea 59: `.pathMatchers("/api/external/**").permitAll()`. JwtAuthenticationFilter saltan paths que inician con `/api/external`. TenantFilter también. **No se requiere ningún cambio en configuración de seguridad.**
4. **TenantContext NO se setea en rutas `/api/external` (ALTO):** TenantFilter extrae `organizationId`/`userId` de JWT claims, pero las rutas `/api/external` no tienen JWT. El UseCase debe resolver `organizationId` desde: token → `porter_enrollment_tokens.organization_id` → lookup organization. NO usar `TenantContext.getOrganizationIdOrThrow()`.
5. **IndexedDB NO usado en frontend (ALTO):** Zero matches para `IndexedDB|IDB|indexedDB|openDB|localForage|Dexie` en `atlas-platform/src/`. Solución: Crear `CryptoStorageService` desde cero.
6. **WebCrypto API NO usado en frontend (ALTO):** Zero matches para `crypto.subtle|CryptoKey|importKey|SubtleCrypto` en `atlas-platform/src/`. Solución: Implementar `crypto.subtle.importKey()` + `extractable: false`.
7. **`manifest.webmanifest` solo tiene favicon 48x48 (BLOQUEANTE):** Chrome requiere iconos ≥192x192 para disparar `beforeinstallprompt`. Sin estos iconos, `PwaUpdateService.canInstall` NUNCA será `true` y el botón "Instalar" no funcionará. Solución: Agregar 192x192 + 512x512 PNG con `"purpose": "any maskable"`.
8. **`PwaUpdateService` ya tiene `promptInstall()` (POSITIVO):** Verificado: captura `beforeinstallprompt`, expone `canInstall` signal, `promptInstall()` retorna `Promise<boolean>`. Reutilizable directamente.
9. **`StorageGateway` solo usa localStorage (ALTO):** `StorageAdapter` wrappea `window.localStorage` con `JSON.stringify/parse`. NO puede almacenar `CryptoKey` objects (no serializables a JSON). Solución: Crear `CryptoStorageService` separado (no modificar `StorageGateway` existente).
10. **No existe servicio de sincronización periódica (MEDIO):** La HU requiere sync en segundo plano post-enrolamiento para claves actualizadas y listas de revocaciones. Solución: Crear `DeviceSyncService` con `setInterval` + `isOnline` signal.

**Análisis de dependencias:** Backend (Hitos 1-6) y frontend domain/infra (Hitos 7-8) son independientes y pueden desarrollarse en paralelo. La integración ocurre en Hito 9. HU #5 depende de HU #4 (tablas `porters`, `porter_enrollment_tokens`, roles, permisos en V13).

**Impacto en consumidores:** Todos los endpoints son nuevos (`GET /api/external/porter/validate-token`, `POST /api/external/porter/enroll`). No hay impacto en APIs existentes. La migración V14 agrega una tabla nueva sin alterar estructuras existentes. El manifest update agrega iconos sin quitar nada.

**Contratos API:**

- `POST /api/external/porter/enroll` → Público → Request: `{ token, deviceInfo: { platform, model, appVersion, userAgent } }` → Response: `{ porterId, porterDisplayName, organizationName, verificationKeyJwk, keyId, maxClockSkewMinutes }` (200 OK)

### Notas Técnicas

- **Generación de claves EdDSA en Java 21:** `KeyPairGenerator.getInstance("Ed25519")` es nativo. No requiere BouncyCastle. La clave pública es 32 bytes, la privada 32 bytes.
- **Formato JWK para Ed25519:** `{ "kty": "OKP", "crv": "Ed25519", "x": "<base64url-encoded-public-key>" }`. Solo `x` para la clave pública. Para la privada se agrega `"d": "<base64url-encoded-private-key>"` (almacenada cifrada, no en JWK plano).
- **WebCrypto import en frontend:** `crypto.subtle.importKey('jwk', { kty: 'OKP', crv: 'Ed25519', x: '...' }, { name: 'Ed25519' }, false, ['verify'])`. El flag `extractable: false` impide exportación via JS.
- **IndexedDB para CryptoKey:** IndexedDB soporta structured cloning de `CryptoKey` directamente. No requiere serialización manual.
- **Master key para cifrado de clave privada backend:** Definir en `application.yml` como `atlas.crypto.master-key` (env variable en producción). Usar `AES/GCM/NoPadding` con IV aleatorio de 12 bytes.
- **Lazy key generation:** Primera vez que se enrola un dispositivo en una organización que no tiene claves, `EnrollPorterDeviceUseCase` genera automáticamente el par EdDSA y lo persiste. Organizaciones sin dispositivos no tienen claves innecesarias.
- **Detección de enrolamiento previo (Escenario 5):** `CryptoStorageService.hasEnrollment()` verifica si hay datos en IndexedDB. Si existe, `EnrollmentPageComponent` muestra advertencia de reemplazo con confirmar/cancelar.
- **Reintento sin consumir token (Escenario 6):** El token solo se marca `CONSUMED` al final exitoso del `EnrollPorterDeviceUseCase`. Si falla, el frontend puede reintentar con el mismo token.
- **Tabla separada para claves (no en Organization):** `organization_crypto_keys` es mejor que agregar columnas a `organizations` porque: (1) soporta key rotation (múltiples keys por org con `is_active`), (2) separación de concerns, (3) la clave privada cifrada es un campo largo que no debería estar en una tabla frecuentemente consultada.
- **Ruta pública `/enroll/:token`:** No tiene auth guard. El token en la URL es el mecanismo de autenticación. El wildcard `**` → `/login` no interfiere porque las rutas específicas tienen precedencia en Angular Router.
- **No se modifica SecurityConfig:** Los endpoints bajo `/api/external/**` ya son `permitAll`. Confirmado en SecurityConfig.java línea 59.
- **Patrón de handler público:** Sigue exactamente el patrón establecido por `ExternalAdminHandler` + `ExternalAdminRouterRest` (verificados, 514 y 287 líneas respectivamente).
