# Historia #9: Invitación y Registro de Propietarios + Invitación de Residentes por Propietario

**Estado:** En Desarrollo (Developer)

---

## Historia de Usuario

**Como** administrador con rol `ADMIN_ATLAS` de una organización activa en la plataforma ATLAS,  
**Quiero** generar invitaciones con URL y token de 24 horas para que propietarios se registren en mi organización seleccionando su unidad, y que los propietarios registrados (`OWNER`) puedan a su vez invitar residentes a su misma unidad con el mismo mecanismo de invitación,  
**Para** incorporar de forma segura y autónoma a los propietarios y residentes de mi propiedad horizontal, estableciendo la cadena de permisos adecuada para la gestión de autorizaciones de ingreso.

## Descripción

Se requiere implementar el flujo completo de invitación y registro de propietarios y residentes en la PWA atlas-platform. El flujo tiene dos partes principales: (1) El `ADMIN_ATLAS` genera una invitación (URL con token de 24h, single-use) desde la opción "Invitaciones" ubicada en el menú "Más" (tres puntos). El propietario abre el link, se le solicita instalar la PWA, completa un formulario de registro con selección de unidad por autocomplete, y queda con estado `ACTIVE` y rol `OWNER`. Se permite más de un propietario por unidad. (2) El `OWNER` puede invitar residentes de su misma unidad desde un botón FAB central en su menú inferior de navegación. El residente recibe la URL, instala la PWA, completa registro (sin autocomplete de unidad, ya que viene del token), y queda `ACTIVE` con rol `RESIDENT`. Existe una configuración a nivel de organización que permite habilitar la administración granular de permisos por propietario: si está activa, el Owner selecciona qué permisos otorgar al residente al momento de invitar; si está inactiva, el residente hereda los mismos permisos del Owner. Si al registrarse el usuario ya existe por documento o email en el sistema, se autocompletan los datos del formulario. Tanto admin como owners pueden ver un historial de invitaciones con filtros.

## Criterios de Aceptación

### Escenario 1: Generación exitosa de invitación para propietarios (ADMIN_ATLAS)

- **Dado** que el administrador `ADMIN_ATLAS` está autenticado y accede a la opción "Invitaciones" dentro del menú "Más" (ícono de tres puntos) en la barra de navegación inferior
- **Cuando** presiona el botón "Generar invitación para propietarios"
- **Entonces** el sistema genera una URL con un token único de 24 horas asociado a `organizationId` y tipo `OWNER_INVITE`, muestra la URL generada con un botón "Copiar" para facilitar su distribución, registra el evento de auditoría `OWNER_INVITE_CREATED`, y la invitación aparece en el historial con estado "Pendiente"

### Escenario 2: Acceso a URL de invitación con token válido — Pantalla de descarga PWA

- **Dado** que un propietario recibió una URL de invitación con un token válido y no consumido
- **Cuando** abre la URL en el navegador de su dispositivo
- **Entonces** el sistema valida el token sin consumirlo, muestra una pantalla informativa con el mensaje "Descarga/instala la aplicación ATLAS" con un botón "Abrir en la App" e instrucciones para instalar la PWA, y el prompt de instalación nativo del navegador se activa (usando `PwaUpdateService.promptInstall()` y descargar la pwa)

### Escenario 3: Token inválido al acceder a URL de invitación

- **Dado** que un usuario accede a una URL de invitación con un token inválido o malformado
- **Cuando** el sistema valida el token contra el backend
- **Entonces** se muestra un mensaje de error: "El enlace de invitación es inválido. Solicita un nuevo enlace al administrador de tu conjunto" y NO se muestra ningún formulario ni opción de instalación

### Escenario 4: Token expirado al acceder a URL de invitación

- **Dado** que un usuario accede a una URL de invitación con un token cuyas 24 horas de vigencia ya expiraron
- **Cuando** el sistema valida el token contra el backend
- **Entonces** se muestra un mensaje de error: "El enlace de invitación ha expirado. Solicita un nuevo enlace al administrador de tu conjunto" y NO se muestra el formulario de registro

### Escenario 5: Token ya consumido al acceder a URL de invitación

- **Dado** que un usuario accede a una URL de invitación con un token que ya fue utilizado por otro usuario
- **Cuando** el sistema valida el token contra el backend y recibe estado `CONSUMED`
- **Entonces** se muestra un mensaje de error: "Este enlace de invitación ya fue utilizado. Si ya te registraste, inicia sesión normalmente" con un enlace/botón para ir a `/login`

### Escenario 6: Registro exitoso de propietario con selección de unidad (autocomplete)

- **Dado** que el propietario abrió la PWA desde un token válido de tipo `OWNER_INVITE` y está en el formulario de registro
- **Cuando** completa todos los campos obligatorios: nombre completo, tipo de documento (por defecto: Cédula), número de documento, teléfono, email (opcional), contraseña, confirmación de contraseña, y selecciona una unidad mediante el autocomplete (que filtra por las unidades de la organización del token, buscando por código como "A-102"), y presiona "Registrarme"
- **Entonces** el sistema valida los datos, crea el usuario con estado `ACTIVE` y rol `OWNER`, lo asocia a la `organizationId` del token y al `unitId` seleccionado, consume el token (marca `consumedAt` y `consumedBy`), registra auditoría `OWNER_JOINED_ORG`, y redirige al usuario a `/home` con acceso completo

### Escenario 7: Autocompletado de datos por documento o email existente

- **Dado** que un usuario está completando el formulario de registro (propietario o residente)
- **Cuando** ingresa un número de documento o email que ya existe en el sistema
- **Entonces** el sistema autocompleta automáticamente los campos restantes del formulario (nombre completo, tipo de documento, teléfono, email) con los datos existentes, permitiendo al usuario verificar y ajustar si es necesario antes de confirmar el registro

### Escenario 8: Múltiples propietarios por unidad

- **Dado** que una unidad (ej. "A-102") ya tiene uno o más propietarios registrados
- **Cuando** otro propietario se registra mediante una invitación y selecciona la misma unidad en el autocomplete
- **Entonces** el sistema permite el registro exitosamente, asociando al nuevo propietario a la misma unidad sin afectar a los propietarios existentes. Ambos propietarios tienen los mismos permisos sobre la unidad

### Escenario 9: Validación de políticas de contraseña en registro

- **Dado** que un usuario (propietario o residente) está en el formulario de registro
- **Cuando** ingresa una contraseña que no cumple la política de seguridad (mínimo 8 caracteres, al menos 1 mayúscula, 1 minúscula y 1 número)
- **Entonces** el sistema muestra un mensaje de validación en tiempo real debajo del campo: "Debe contener mayúscula, minúscula y número (mínimo 8 caracteres)" y el botón "Registrarme" permanece deshabilitado

### Escenario 10: Contraseñas no coinciden en registro

- **Dado** que un usuario está en el formulario de registro
- **Cuando** ingresa una contraseña y una confirmación que no coinciden
- **Entonces** el sistema muestra un mensaje de validación debajo del campo de confirmación: "Las contraseñas no coinciden" y el botón "Registrarme" permanece deshabilitado

### Escenario 11: Generación de invitación para residentes (OWNER)

- **Dado** que un propietario con rol `OWNER` está autenticado, deben aperecer tres bottones en el menu el primero es el de ver historia de autirizaciones y grande naranja del medio es para genera autoriazaciones y el del lado derecho cva ahcer para ir a una ivsa donde va a poder vr todos los recidentes de sum propiedada incativar si es el caso y tambien va a poder ingresar mas generanol el link con un timepo de expiracion de 24h y copiandolo
- **Cuando** selecciona la opción "Residentes"
- **Entonces** el sistema muestra una vista donde va  a poder ver el listado y posteriro un botn + para  genera una URL con un token único de 24 horas asociado a `organizationId`, `unitId` del propietario, y tipo `RESIDENT_INVITE`, muestra la URL generada con botón "Copiar", registra auditoría `RESIDENT_INVITE_CREATED`, y la invitación aparece en el historial del propietario

### Escenario 12: Configuración activa — Owner selecciona permisos al invitar residente

- **Dado** que la organización tiene activada la configuración "Habilitar administración de permisos por propietario" (checkbox en la sección de Configuración), debes agregar ese campo en el formulario de configuraciones
- **Cuando** el `OWNER` genera una invitación para un residente
- **Entonces** antes de generar la URL, el sistema muestra una pantalla de selección de permisos con checkboxes donde el Owner puede elegir qué permisos otorgar al residente (ej. crear autorizaciones, editar, eliminar, ver/listar). Los permisos seleccionados se asocian al token y se asignan al residente al completar su registro

### Escenario 13: Configuración inactiva — Residente hereda permisos del Owner

- **Dado** que la organización NO tiene activada la configuración "Habilitar administración de permisos por propietario"
- **Cuando** el `OWNER` genera una invitación para un residente
- **Entonces** el sistema genera la URL directamente sin mostrar selección de permisos. El token lleva los mismos permisos que tiene el Owner, y al completar el registro el residente recibe los mismos permisos de autorizaciones que el propietario

### Escenario 14: Registro exitoso de residente (sin autocomplete de unidad)

- **Dado** que un residente abrió la PWA desde un token válido de tipo `RESIDENT_INVITE` y está en el formulario de registro
- **Cuando** completa los campos obligatorios: nombre completo, tipo de documento (por defecto: Cédula), número de documento, teléfono, email (opcional), contraseña y confirmación de contraseña (la unidad NO se muestra porque viene del token)
- **Entonces** el sistema valida los datos, crea el usuario con estado `ACTIVE` y rol `RESIDENT`, lo asocia a la `organizationId` y `unitId` del token, asigna los permisos según la configuración (heredados o seleccionados por el Owner), consume el token, registra auditoría `RESIDENT_JOINED_UNIT`, y redirige a `/home`

### Escenario 15: Historial de invitaciones — ADMIN_ATLAS con filtros

- **Dado** que el `ADMIN_ATLAS` accede a la pantalla "Invitaciones" desde el menú "Más"
- **Cuando** se carga la vista
- **Entonces** se muestra una tabla con todas las invitaciones de la organización (propietarios y residentes), con las columnas: tipo de invitación, estado (Pendiente/Consumida/Expirada), fecha de creación, fecha de expiración, unidad asociada, invitado (nombre si fue consumida), y filtros por: unidad, persona/usuario, rango de fechas, y estado

### Escenario 16: Historial de invitaciones — OWNER y RESIDENT (solo su unidad)

- **Dado** que un usuario con rol `OWNER` o `RESIDENT` accede a la sección de invitaciones de su unidad
- **Cuando** se carga la vista
- **Entonces** se muestran únicamente las invitaciones relacionadas con su unidad específica, con la misma información pero filtrada automáticamente por su `unitId`

### Escenario 17: Configuración de organización — Checkbox de administración de permisos

- **Dado** que el `ADMIN_ATLAS` accede a la sección "Configuración" de su organización, esa ocpion de ocnfiguracion solo es para el ADMIN_ATLAS
- **Cuando** visualiza las opciones configurables
- **Entonces** se muestra un checkbox con la etiqueta "Habilitar administración de permisos por propietario" con una descripción explicativa: "Si está activo, los propietarios podrán seleccionar qué permisos otorgar a los residentes que inviten. Si está inactivo, los residentes heredarán los mismos permisos del propietario". El cambio se persiste al guardar la configuración

### Escenario 18: Error de conexión durante registro

- **Dado** que un usuario está completando el formulario de registro (propietario o residente)
- **Cuando** el backend no está disponible o la petición excede el tiempo de espera
- **Entonces** el sistema muestra un mensaje de error: "No se puede conectar con el servidor. Verifica tu conexión a internet e intenta nuevamente" y el formulario permanece con los datos ingresados para reintentar

## Información Recopilada

### Usuario y Contexto

- **Tipo de usuario:** `ADMIN_ATLAS` (genera invitaciones para propietarios y ve historial completo), `OWNER` (se registra vía invitación, genera invitaciones para residentes de su unidad, ve historial de su unidad), `RESIDENT` (se registra vía invitación del Owner, ve historial de su unidad)
- **Permisos requeridos:** `ADMIN_ATLAS` requiere permisos de gestión de invitaciones. `OWNER` requiere permisos de autorizaciones (CRUD: crear, editar, eliminar, ver/listar) + permiso exclusivo de invitar residentes a su unidad. `RESIDENT` requiere permisos de autorizaciones (por defecto iguales al Owner, configurables si la opción de administración de permisos está activa)
- **Valor de negocio:** Permitir la incorporación autónoma y segura de propietarios y residentes a la plataforma ATLAS, estableciendo una cadena de responsabilidad donde el admin invita propietarios y los propietarios invitan a sus residentes, manteniendo la integridad del modelo multi-tenant y la trazabilidad de cada invitación

### Reglas de Negocio

1. **Token de invitación — Expiración:** Todo token de invitación (OWNER_INVITE y RESIDENT_INVITE) expira en 24 horas desde su generación
2. **Token de invitación — Single-use:** Cada token es de un solo uso. Se persiste `consumedAt` (timestamp) y `consumedBy` (userId) al completar el registro. Protección contra replay
3. **Token OWNER_INVITE:** Asociado a `organizationId` y tipo `OWNER_INVITE`. No lleva `unitId` porque el propietario selecciona su unidad al registrarse
4. **Token RESIDENT_INVITE:** Asociado a `organizationId`, `unitId` del Owner que invita, tipo `RESIDENT_INVITE`, y opcionalmente los permisos seleccionados por el Owner
5. **Múltiples propietarios por unidad:** Se permite que una misma unidad tenga más de un propietario registrado. Todos tienen los mismos permisos sobre la unidad
6. **Owner solo invita residentes de su unidad:** Un propietario solo puede generar invitaciones para residentes vinculados a su `unitId`, no puede invitar a otras unidades
7. **Configuración de permisos por propietario:** Si el checkbox "Habilitar administración de permisos por propietario" está activo en la configuración de la organización, el Owner selecciona qué permisos otorgar al residente. Si está inactivo, el residente hereda los mismos permisos del Owner
8. **Autocompletado por duplicado:** Si al registrarse un usuario ingresa un número de documento o email que ya existe en el sistema, los datos del formulario se autocompletan con la información existente
9. **Políticas de contraseña:** Mínimo 8 caracteres, al menos 1 mayúscula, 1 minúscula y 1 número (consistente con HU #2)
10. **Mensajes de error diferenciados por token:** Token inválido, token expirado y token consumido muestran mensajes distintos (consistente con HU #2)
11. **State machine:** Owner y Resident siguen el flujo: `PENDING_INVITE` → `ACTIVE` al completar el registro exitosamente
12. **Auditoría obligatoria:** Eventos registrados: `OWNER_INVITE_CREATED`, `OWNER_JOINED_ORG`, `RESIDENT_INVITE_CREATED`, `RESIDENT_JOINED_UNIT`
13. **Multi-tenant estricto:** Tokens llevan `organizationId`. Las unidades del autocomplete se filtran por la organización del token. Los datos del historial se filtran por organización (admin) o por unidad (owner/resident)

### Interfaz y Navegación

- **ADMIN_ATLAS — Pantalla "Invitaciones":** Accesible desde el menú "Más" (ícono de tres puntos `•••`) en la barra de navegación inferior. Contiene: botón "Generar invitación para propietarios" + tabla con historial de invitaciones con filtros (unidad, persona/usuario, fechas, estado)
- **OWNER — Botón FAB central:** Botón circular "+" centrado y prominente en el menú inferior de navegación del propietario. Al presionar, muestra opciones incluyendo "Invitar residente". También puede acceder a ver el historial de invitaciones y residentes de su unidad
- **RESIDENT — Vista de su unidad:** Puede ver el historial de invitaciones de su unidad (solo lectura)
- **Formulario de registro (Owner):** Nombre completo, tipo documento (default: Cédula), número documento, teléfono, email (opcional), contraseña, confirmación contraseña, unidad (autocomplete filtrado por organización del token, búsqueda por código ej. "A-102")
- **Formulario de registro (Resident):** Igual al Owner pero SIN campo de unidad (la unidad viene del token automáticamente)
- **Pantalla web de invitación (pre-PWA):** Validación de token + pantalla de descarga/instalación de la PWA + botón "Abrir en la App"

### Sistemas Externos (Si aplica)

No hay integración con sistemas externos. Todo el flujo opera dentro del ecosistema ATLAS (backend + PWA).

### Decisiones de Diseño

**Patrón Arquitectónico:** Clean Architecture (Bancolombia) en Backend + Atomic Design en Frontend — Extensión del modelo de invitaciones existente

**Justificación:** El sistema ya posee un modelo de invitaciones funcional (`Invitation`, `InvitationUseCase`, `OwnerActivationUseCase`) parcialmente implementado para flujos admin→owner (HU #3/#4). En lugar de crear un sistema paralelo de tokens (como ocurrió con `PorterEnrollmentToken` vs `AdminActivationToken`), se decidió **extender el modelo `Invitation` existente** para cubrir los dos nuevos flujos (ADMIN→OWNER self-register, OWNER→RESIDENT). Esto maximiza reutilización de código, reduce duplicación y mantiene coherencia con el `InvitationRepository`, `InvitationAuditRepository` y los patrones de auditoría ya implementados. El diseño respeta estrictamente los estándares documentados en `CODING_STANDARDS.md` y `coding-standards.md`: nomenclatura en inglés, Clean Architecture por capas, Gateway→Adapter con DI, `Result<T>` pattern, Signals + OnPush en Angular, programación reactiva `Mono<T>/Flux<T>` en backend, path aliases `@domain/*`, `@infrastructure/*`, `@presentation/*`, y Atomic Design para componentes frontend.

**Componentes Afectados:**

#### Backend — 8 Componentes Modificados

- **`InvitationType` (Modificación):** Agregar `OWNER_SELF_REGISTER` y `RESIDENT_INVITE` al enum existente.
  - Nivel de cambio: Menor
  - Especificaciones: Se añaden dos nuevos valores al enum en `co.com.atlas.model.invitation.InvitationType`. Los valores existentes (`ORG_MEMBER`, `UNIT_OWNER`, `UNIT_TENANT`, `UNIT_FAMILY`, `OWNER_INVITATION`) se mantienen intactos.

- **`InvitationUseCase` (Modificación):** Agregar 4 métodos al use case existente para los nuevos flujos de invitación y registro.
  - Nivel de cambio: Mayor
  - Especificaciones: `createOwnerInvitation(Long orgId, Long invitedBy)` → genera token UUID 24h single-use tipo `OWNER_SELF_REGISTER` sin `unitId` ni `email`, retorna `Mono<Invitation>` con URL construida. `createResidentInvitation(Long orgId, Long unitId, Long invitedBy, String permissionsJson)` → genera token con `unitId` + permisos en `initialPermissions`, tipo `RESIDENT_INVITE`. `acceptOwnerSelfRegister(String token, OwnerRegistrationData data, Long unitId)` → valida token, crea/actualiza usuario (`ACTIVE`), asigna rol `OWNER` vía `UserRoleMulti`, crea `UserUnit(OWNER)` + `UserOrganization`, consume token (`ACCEPTED`), audita `ACTION_ACCEPTED`. `acceptResidentRegister(String token, ResidentRegistrationData data)` → similar pero `unitId` viene del token, rol `RESIDENT` vía `UserRoleMulti`, permisos del `initialPermissions` del token.

- **`InvitationRepository` (Modificación):** Agregar métodos para consulta con filtros dinámicos.
  - Nivel de cambio: Menor
  - Especificaciones: `findByOrganizationIdWithFilters(Long orgId, InvitationFilters filters)` → `Flux<Invitation>`. `findByUnitIdWithFilters(Long unitId, InvitationFilters filters)` → `Flux<Invitation>`. Implementación en adapter usando `DynamicQueryBuilder` (patrón establecido en HU #8).

- **`OrganizationConfiguration` (Modificación):** Agregar campo para configuración de permisos granulares.
  - Nivel de cambio: Menor
  - Especificaciones: Agregar `Boolean enableOwnerPermissionManagement` (default `false`) al modelo de dominio `co.com.atlas.model.organization.OrganizationConfiguration`.

- **`OrganizationSettings` (Modificación):** Agregar campo correspondiente al settings model.
  - Nivel de cambio: Menor
  - Especificaciones: Agregar `Boolean enableOwnerPermissionManagement` a `co.com.atlas.model.organization.OrganizationSettings` con default `false`.

- **`AuthUserRepository` (Verificación):** Ya dispone de `existsByDocumentTypeAndNumber()` y `findByDocumentTypeAndNumber()` — verificado que retorna `Mono<AuthUser>` completo. También tiene `existsByEmail()` y `findByEmail()`.
  - Nivel de cambio: Ninguno (verificado, funciona para autocompletado)

- **`UnitRepository` (Modificación):** Agregar método de búsqueda para autocomplete.
  - Nivel de cambio: Menor
  - Especificaciones: `searchByOrganizationIdAndCodePrefix(Long orgId, String prefix)` → `Flux<Unit>` con `LIMIT 20` y `ILIKE` para búsqueda por código de unidad (ej. "A-102").

- **`OrganizationSettingsUseCase` (Modificación):** Extender lectura/escritura del nuevo campo.
  - Nivel de cambio: Menor
  - Especificaciones: Los métodos `getSettings()` y `updateSettings()` ya existentes deben incluir `enableOwnerPermissionManagement` en la serialización/deserialización.

#### Backend — 8 Componentes Nuevos

- **`ResidentRegistrationData` (Nuevo — domain/usecase/invitation/):** DTO para datos de registro de residente. Campos: `names` (String), `phone` (String), `documentType` (DocumentType), `documentNumber` (String), `password` (String). Patrón: `@Getter`, `@Builder`, `@AllArgsConstructor`. Análogo a `OwnerRegistrationData` existente.

- **`InvitationFilters` (Nuevo — domain/model/invitation/):** Modelo de filtros para consultas al historial. Campos: `InvitationType type`, `InvitationStatus status`, `Long unitId`, `String search`, `Instant dateFrom`, `Instant dateTo`. Patrón: `@Getter`, `@Builder`, `@AllArgsConstructor`.

- **`OwnerInvitationHandler` (Nuevo — entry-points/reactive-web/api/invitation/):** `@Component @RequiredArgsConstructor @Slf4j`. Métodos: `createOwnerInvitation(ServerRequest)` → extrae `orgId` de `TenantContext`, delega a `InvitationUseCase.createOwnerInvitation()`, retorna `Mono<ServerResponse>` con `ApiResponse<Invitation>`. `acceptOwnerRegistration(ServerRequest)` → endpoint externo (sin auth), recibe body DTO con token + datos + `unitId`, delega a `acceptOwnerSelfRegister()`.

- **`ResidentInvitationHandler` (Nuevo — entry-points/reactive-web/api/invitation/):** `@Component @RequiredArgsConstructor @Slf4j`. `createResidentInvitation(ServerRequest)` → extrae `orgId`/`unitId` de TenantContext, lee `enableOwnerPermissionManagement` de config, si activo requiere body con permisos; si inactivo hereda permisos del owner. `acceptResidentRegistration(ServerRequest)` → endpoint externo.

- **`InvitationHistoryHandler` (Nuevo — entry-points/reactive-web/api/invitation/):** `@Component @RequiredArgsConstructor @Slf4j`. `getInvitationHistory(ServerRequest)` → recibe filtros como query params (`type`, `status`, `unitId`, `search`, `dateFrom`, `dateTo`), aplica data scoping: si rol `ADMIN_ATLAS` → filtra por `organizationId`; si `OWNER`/`RESIDENT` → filtra por `unitId` del usuario. Usa `TenantContext.getRoles()` (patrón HU #8).

- **`OwnerInvitationRouterRest` (Nuevo — entry-points/reactive-web/api/invitation/):** `@Configuration @Tag(name = "Owner Invitations")`. ### Validación de Impacto

Se realizó validación técnica exhaustiva verificando código real del proyecto. Hallazgos críticos:

1. **Modelo `Invitation` existente es extensible:** El modelo ya tiene `invitationToken`, `type` (enum), `status` (enum), `initialPermissions` (JSON String), `unitId`, `organizationId`, `invitedBy`, `expiresAt`, `acceptedAt`. Todos los campos necesarios para los nuevos flujos ya existen en la tabla. Solo se requiere agregar nuevos valores al enum `InvitationType`.

2. **`InvitationUseCase` ya tiene el patrón base:** Los métodos `acceptByToken()`, `acceptWithOwnerData()`, `createMembership()` y `ensureUserExists()` proporcionan la base para los nuevos flujos. Los nuevos métodos (`createOwnerInvitation`, `acceptOwnerSelfRegister`, `createResidentInvitation`, `acceptResidentRegister`) siguen el mismo patrón reactivo establecido.

3. **`OwnerActivationUseCase` valida patrones de contraseña:** El método `isPasswordStrong()` (upper + lower + digit, min 8) ya existe y puede reutilizarse directamente en los nuevos flujos de registro.

4. **`AuthUserRepository.findByDocumentTypeAndNumber()` retorna `Mono<AuthUser>` completo:** Verificado que incluye todos los campos necesarios para autocompletar formularios (`names`, `email`, `phone`, `documentType`, `documentNumber`). NO se requiere modificación.

5. **`PwaUpdateService.promptInstall()` funcional:** Signal `canInstall`, `isInstalled`, método `promptInstall()` — reutilizable directamente sin modificación.

6. **`ActivatePageComponent` es el patrón exacto a replicar:** Estados de página vía signals, `OnInit` con extracción de token de query params, validación asíncrona, formulario condicional, manejo de éxito + modal PWA. El nuevo `InvitationRegisterPageComponent` replica este patrón probado.

7. **NO existe gateway/adapter de invitaciones en frontend:** Verificado que no hay `InvitationGateway` ni `InvitationAdapter`. Se requiere creación completa (nuevo dominio frontend).

8. **`admin-bottom-nav` tiene menú "Más" (three dots):** Verificado que el componente ya implementa el patrón de menú expandible. Agregar "Invitaciones" es una modificación menor.

9. **NO existe `bottom-nav` con FAB central:** El `bottom-nav` genérico y `doorman-bottom-nav` no tienen botón FAB. Se requiere crear `owner-bottom-nav` como nuevo organismo.

10. **`DynamicQueryBuilder` (HU #8) reutilizable:** Este utilitario para queries dinámicas con filtros combinables ya existe en el backend y puede aplicarse al historial de invitaciones.

11. **`TenantContext.getRoles()`/`getPrimaryRole()` disponible (HU #8):** Permite data scoping por rol en el handler del historial sin lógica adicional.

12. **Riesgo controlado — `InvitationUseCase` creciendo:** Actualmente ~300+ líneas. Con 4 métodos nuevos podría acercarse al límite SRP. Mitigación: si crece demasiado, extraer a `OwnerRegistrationUseCase` y `ResidentRegistrationUseCase` como use cases separados que compongan con `InvitationUseCase`.

### Notas Técnicas (Si aplica)

**Token sin email asociado (by design):** A diferencia de HU #2 (activación admin con email conocido), los tokens de invitación en HU #9 son genéricos — no están vinculados a un email específico. Cualquier persona con el link puede registrarse. Esto es intencional según los requerimientos del PO (distribución vía WhatsApp/SMS). El token UUID + expiración 24h + single-use proporcionan seguridad suficiente. Se recomienda considerar rate-limiting y CAPTCHA en fases futuras.

**Schema JSON para `initialPermissions`:** Se define el formato estricto que se almacenará en el campo `initialPermissions` del modelo `Invitation`:
```json
{"create": true, "edit": true, "delete": false, "view": true}
```
Validar en el use case que las keys sean exactamente las esperadas.

**Autocomplete de unidades — Performance:** Usar `ILIKE` con `LIMIT 20` y debounce 300ms (mínimo 2 caracteres) en frontend. Si la organización tiene >1000 unidades, considerar índice en `units.code` para la columna.

**Componentes frontend — Decisión `ui/` vs `pages/components/`:** Siguiendo estrictamente el estándar de `CODING_STANDARDS.md`, los formularios de registro, autocompletado de unidad, selector de permisos y filtros de invitaciones son **específicos de estas páginas** y no se reutilizarán en otras. Por tanto, se crean dentro de `pages/<page>/components/`. Solo `owner-bottom-nav` va en `ui/organisms/` porque es un componente de navegación global para el rol OWNER.

#### Decisiones Técnicas

1. **Migración V16 (no V15):** V15 ya existía (HU #4). Se usó V16.
2. **DynamicQueryBuilder:** Utilidad genérica reutilizable para construir queries SQL con filtros dinámicos. Soporta `where`, `whereOptional`, `whereOptionalIlike`, `whereOptionalIlikePrefix`, `whereOptionalBetween`, `orderBy`, `limit`. 11 tests unitarios.
3. **UserLookupUseCase (refactoring):** Creado durante auditoría para resolver violación Clean Architecture — `UserLookupHandler` inyectaba repositorios directamente. Ahora delega a use case.
4. **InvitationHistoryHandler simplificado (refactoring):** El scoping de datos por rol (ADMIN vs OWNER/RESIDENT) se movió al `InvitationUseCase.getInvitationHistory()` para respetar Clean Architecture.
5. **Password matching en use case (refactoring):** La validación de contraseñas coincidentes se movió de `ResidentInvitationHandler` al `InvitationUseCase.acceptResidentRegister()`. Se agregó campo `confirmPassword` a `ResidentRegistrationData`.
6. **Formularios como organismos en `/ui/organisms/`:** Los formularios `owner-registration-form` y `resident-registration-form` se ubicaron en `presentation/ui/organisms/` (no en `pages/invitation-register/components/`) por consistencia con el patrón de la aplicación.
7. **Autocomplete de unidad integrado en formulario:** En lugar de crear un componente separado `unit-autocomplete`, se integró la funcionalidad directamente en `owner-registration-form` usando `SearchUnitsUseCase` y `debounceTime(300)`.
8. **PWA install integrado en página:** En lugar de crear un componente separado `pwa-install-prompt`, se maneja el flujo de instalación PWA directamente en `invitation-register-page` post-registro exitoso.
