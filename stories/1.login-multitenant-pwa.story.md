# Historia #1: Integrar Login Multitenant en PWA Atlas Platform

**Estado:** Borrador (PO)

---

## Historia de Usuario

**Como** usuario registrado de la plataforma Atlas (cualquier rol: Administrador Atlas, Administrador de Conjunto, Residente o Portero/Vigilante),  
**Quiero** iniciar sesión en la PWA atlas-platform utilizando mis credenciales (email y contraseña) y que el sistema me autentique contra el backend real obteniendo mis datos y la organización a la que pertenezco,  
**Para** acceder de forma segura a las funcionalidades de la plataforma manteniendo coherencia con el esquema de autenticación multitenant existente en el backend Atlas.

## Descripción

Se requiere integrar el sistema de login real multitenant en la PWA atlas-platform, reemplazando el mock interceptor actual por llamadas al backend Atlas real. La PWA ya cuenta con un componente de login existente (`LoginPageComponent` → `LoginTemplateComponent` → `LoginFormComponent`) que debe ser reutilizado y adaptado. El flujo será de una sola fase: el usuario ingresa credenciales, el backend autentica y retorna un JWT con los datos del usuario, roles, permisos y la organización a la que pertenece. Tras el login exitoso, se redirige a la vista `/home`. Se debe crear una estructura de environments para configurar el dominio del backend, implementar un AuthGuard funcional listo para proteger rutas, y reemplazar completamente el mock interceptor por la integración con la API real del backend. Se deben mostrar mensajes de error diferenciados para cada tipo de fallo.

---

## Criterios de Aceptación

### Escenario 1: Login exitoso con credenciales válidas

- **Dado** que el usuario está en la pantalla de login (`/login`) y el backend Atlas está disponible
- **Cuando** ingresa un email y contraseña válidos de un usuario activo con organización asignada y presiona "Iniciar Sesión"
- **Entonces** el sistema autentica contra `POST /api/auth/login` del backend real, almacena el JWT recibido (que incluye userId, email, roles, permissions, organizationId, enabledModules), y redirige al usuario a la vista `/home`

### Escenario 2: Error por credenciales inválidas

- **Dado** que el usuario está en la pantalla de login
- **Cuando** ingresa un email o contraseña incorrectos y presiona "Iniciar Sesión"
- **Entonces** el sistema muestra un mensaje de error claro: "Las credenciales ingresadas son incorrectas. Verifica tu correo y contraseña" sin revelar cuál de los dos campos es incorrecto, y el formulario permanece habilitado para reintentar

### Escenario 3: Error por usuario desactivado/inactivo

- **Dado** que el usuario está en la pantalla de login
- **Cuando** ingresa credenciales de un usuario con estado inactivo
- **Entonces** el sistema muestra un mensaje de error específico: "Tu cuenta se encuentra desactivada. Contacta al administrador de tu conjunto" y no permite el acceso

### Escenario 4: Error por cuenta sin organización asignada

- **Dado** que el usuario está en la pantalla de login
- **Cuando** ingresa credenciales válidas de un usuario que no tiene ninguna organización asignada
- **Entonces** el sistema muestra un mensaje de error específico: "Tu cuenta no tiene una organización asignada. Contacta al administrador" y no permite el acceso

### Escenario 5: Error por token expirado durante navegación

- **Dado** que el usuario está autenticado y navega por la aplicación
- **Cuando** el token JWT ha expirado y se realiza una petición al backend que retorna 401
- **Entonces** el sistema limpia la sesión almacenada (localStorage), muestra un mensaje informativo "Tu sesión ha expirado. Por favor inicia sesión nuevamente" y redirige automáticamente a `/login`

### Escenario 6: Error de conexión o timeout

- **Dado** que el usuario está en la pantalla de login
- **Cuando** intenta iniciar sesión pero el backend no está disponible o la petición excede el tiempo de espera (timeout)
- **Entonces** el sistema muestra un mensaje de error: "No se puede conectar con el servidor. Verifica tu conexión a internet e intenta nuevamente" y el formulario permanece habilitado para reintentar

### Escenario 7: AuthGuard bloquea acceso sin autenticación

- **Dado** que existe un AuthGuard funcional implementado en la PWA
- **Cuando** un usuario no autenticado intenta acceder a una ruta protegida (cuando se aplique el guard en el futuro)
- **Entonces** el AuthGuard redirige al usuario a `/login` y el guard está disponible como `CanActivateFn` para ser aplicado a las rutas cuando se requiera

### Escenario 8: Configuración de entornos con API real

- **Dado** que la PWA tiene configurados los archivos de entorno (`environments/`)
- **Cuando** la aplicación se inicia en cualquier entorno (desarrollo, staging, producción)
- **Entonces** las peticiones HTTP se dirigen al dominio del backend configurado en el archivo de entorno correspondiente, y el mock interceptor ha sido completamente reemplazado por la integración real

## Información Recopilada

### Usuario y Contexto

- **Tipo de usuario:** Todos los roles registrados en la plataforma Atlas: `ADMIN_ATLAS`, `ADMIN_CONJUNTO`, `RESIDENTE`, `PORTERO_VIGILANTE`
- **Permisos requeridos:** Credenciales válidas (email + contraseña) y cuenta activa con al menos una organización asignada. Los permisos granulares vienen en el JWT post-login.
- **Valor de negocio:** Habilitar la autenticación real contra el backend multitenant existente, eliminando los datos mock hardcodeados y garantizando coherencia arquitectónica, visual y de seguridad con el ecosistema Atlas

### Reglas de Negocio

- El login es de **una sola fase**: credenciales → JWT con datos + organización del usuario (no se implementa selección de organización por ahora)
- El JWT del backend incluye: `userId`, `email`, `names`, `roles`, `permissions`, `modulePermissions`, `organizationId`, `enabledModules`, `defaultRoute`
- El token se almacena en `localStorage` bajo la clave `auth_token`
- Tras login exitoso se redirige siempre a `/home`
- Los mensajes de error deben ser diferenciados por tipo de fallo (5 tipos: credenciales inválidas, usuario inactivo, sin organización, token expirado, error de conexión)
- No se implementa refresh token por ahora; al expirar el token se redirige a login

### Interfaz

- La pantalla de login ya existe: `LoginPageComponent` → `LoginTemplateComponent` → `LoginFormComponent` (patrón Atomic Design)
- Formulario con campos: email ("Usuario o Correo") y contraseña ("Contraseña"), botón "Iniciar Sesión"
- Los errores se muestran como toast o mensaje en la misma pantalla de login según el design system existente (tokens CSS en `styles.css`)
- Post-login exitoso se redirige a `/home` donde existe `HomeComponent`

### Sistemas Externos

- **Backend Atlas:** API REST en el backend Java/Spring WebFlux. Endpoint principal: `POST /api/auth/login`. La URL base del backend se configura mediante archivos de entorno (`environments/`)

## Contexto y Referencias

**Arquitectura:** Documentación multitenant en `SISTEMA_MULTI_TENANT_DESIGN.md`, `FRONTEND_MULTITENANT_DOCUMENTATION.md`, `QUICK_START_MULTITENANT.md`

**Historias relacionadas:** No existen historias previas. Esta es la primera historia del proyecto.

**Lecciones aprendidas:** 
- El mock interceptor actual (`mockApiInterceptor`) acepta cualquier contraseña y tiene solo 2 usuarios hardcodeados (`admin@atlas.com`, `resident@atlas.com`); debe ser completamente reemplazado
- El `AuthenticationService` existente ya tiene estructura base con manejo de errores (401, 429, timeout) pero apunta al mock; se debe adaptar para API real
- No existe AuthGuard, interceptor de token, ni manejo de sesión expirada en el frontend actual
- El backend usa BCrypt para passwords y HMAC-SHA256 para firmar JWTs
